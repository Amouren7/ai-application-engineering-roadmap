# 05｜RAG 与企业知识库`n`n> 📚 **提示**`n> RAG 的核心不是“接一个向量数据库”，而是让系统在回答前找到对的问题、正确的版本和可引用的证据，并能证明检索是否真的帮助了回答。

# 本章解决什么问题

企业政策、产品手册、实验记录和项目文档会变化，模型训练知识不一定包含它们。直接把所有文件塞进上下文会超长、昂贵且难以追溯。本章完成 P2：一个能返回依据的企业知识助手。

# RAG 最小链路

| 环节 | 必须做什么 | 日常类比 |
|-|-|-|
| Ingest | 读取文件、识别格式、保存来源和版本 | 把新文件登记进档案室 |
| Chunk | 按语义和长度切成可检索片段，保留标题和邻接信息 | 把一本书分成带章节标签的索引卡 |
| Metadata | 记录部门、日期、权限、文档版本、页码或来源 URL | 给档案卡贴上归属、有效期和保密等级 |
| Embedding | 把文本映射成可比较的向量表示 | 把意思相近的卡片放到相近的货架位置 |
| Retrieval | 根据问题找候选片段，并应用权限过滤 | 先从档案室找出可能相关的几张卡 |
| Rerank | 对候选片段重新排序，优先最能回答当前问题的内容 | 档案管理员把最相关的卡放到最上面 |
| Citation | 把答案中的关键判断链接回来源 | 每个结论都附上书名、页码和版本 |
| Evaluation | 用测试问题和参考答案评估检索与回答 | 定期抽查档案员是否找对文件、引用是否准确 |

# 最小必要理论

- Chunk 太大：上下文噪声多；太小：语义断裂。切分应由文档结构、问题类型和测试集决定。
- 向量相似不等于事实相关；关键词、过滤条件、时间和权限仍然重要。
- Hybrid Search 结合关键词和语义检索；Rerank 用更精细的模型或规则重排候选。
- Query Rewrite 可以把用户口语改成更适合检索的查询，但要保留原问题，避免改写偏题。
- 回答必须区分“检索不到”“来源冲突”“来源过期”和“来源支持”。

# 极简案例：员工制度知识助手

用户问“试用期请假怎么计算？”系统先识别问题主题和用户身份，再检索当前生效的制度片段，过滤其无权访问的部门文件，最后返回答案、引用、政策版本和不确定性。

```text
answer: string
citations:
  - document_id: string
    title: string
    version: string
    location: string
    quote: string
confidence: high | medium | low
uncertainties: string[]
if no_supported_source: "无法根据当前知识库确认"
```

# 跟着做：P2 最小闭环

1. 选 20–50 份脱敏文档，建立来源、版本、日期、权限和文档类型清单。
2. 先做关键词检索 baseline，再做向量检索；不要没有 baseline 就声称 RAG 变好了。
3. 实现结构化 chunk 和 metadata，保留原文位置，确保可以回到来源。
4. 加入权限过滤、版本过滤和引用生成；检索结果不足时明确拒答。
5. 建立至少 30 条测试问题，包含答案存在、答案不存在、版本冲突、权限不足和模糊问题。
6. 比较 top-k、chunk 大小、hybrid、rerank 和 query rewrite 对 Recall@k、引用准确率、回答正确率的影响。

# AI Coding 学习方法

让 AI 先画 ingest、retrieve、answer 三条链路，再生成每条链路的测试。要求它解释 embedding、向量库和权限过滤分别承担什么责任。不要让 AI 以“换一个 embedding 模型”代替分析数据切分和测试集。

# 自己修改

- 把 metadata 增加 effective_from 和 effective_to，检索时只允许返回当前有效版本。
- 为每个 citation 增加原文 quote，自动检查 quote 是否真的出现在来源文档。
- 增加一个“权限不足”和一个“知识库为空”的明确响应。
- 用 pgvector 或 Chroma 任选其一完成实现，再写一段迁移另一个存储的设计说明。

# Debug 挑战

| 现象 | 排查重点 |
|-|-|
| 检索不到明明存在的内容 | 解析、chunk、metadata、查询改写、top-k 和权限过滤 |
| 召回了过期政策 | 版本字段、有效期过滤、排序和文档更新流程 |
| 引用存在但不支持结论 | 引用绑定、quote 校验、模型是否越过证据补写 |
| 回答变长但没有变准 | 噪声片段、上下文排序、答案 schema 和测试集分层 |
| 某部门看到了不该看的内容 | 检索前权限过滤、租户隔离、缓存 key 和日志脱敏 |

# 小项目：可评估的企业知识助手

交付一个可导入文档、按权限检索、返回引用和拒答的助手。必须包含：文档清单、索引脚本、查询接口、测试集、baseline 对比、引用检查、失败样例、日志和成本记录。

# 验收标准

- 能独立解释 ingest、chunk、metadata、embedding、retrieval、hybrid、rerank、query rewrite 和 citation 的职责边界。
- 能用测试集证明一次检索策略修改带来了什么变化，并说明指标局限。
- 能处理不存在答案、版本冲突和权限不足，不用模型猜补。
- 能指出向量数据库不是知识库本身，知识库还包括来源、版本、权限和更新流程。
- 能不用教程重做“文档 → 索引 → 检索 → 引用回答”的核心链路。

# 自测与常见误区

- 为什么 RAG 不是把整本书放进 Prompt？因为上下文容量、噪声、成本和可追溯性都更差。
- 为什么 top-k 越大不一定越好？更多候选可能增加噪声并挤掉真正重要的片段。
- 为什么引用链接不等于引用正确？链接可能存在，但片段未支持答案。
- 常见误区：先买向量数据库再找问题；没有 baseline；只测成功问题；忽略权限和版本；把召回相似度当答案正确率。
