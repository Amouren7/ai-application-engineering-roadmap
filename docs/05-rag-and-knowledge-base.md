# 05｜检索增强生成与知识库（RAG）

## 本章开始前：准备与产出

| 项目 | 说明 |
|-|-|
| Python | 第一轮可选；先用三篇短文和关键词检索理解流程，第二轮再用 Python 做检索实验 |
| API Key | 生成回答通常需要；只做导入和检索实验时可以暂缓 |
| 安装软件 | 不急着装向量数据库；先用本地文本和简单检索验证思路 |
| 能否只用网页工具 | 可以用 Dify 知识库体验，但必须检查引用是否真的来自资料 |
| 本章产出 | 一个有文档、检索结果、引用和小测试集的最小知识库助手 |

先理解“资料从哪里来、切成什么、检索出什么、模型看到了什么”，再学习 Embedding、向量库和 Rerank。

> 如果模型不知道公司最新制度，最可靠的第一反应不是“再训练一次”，而是先查到正确资料，再把资料交给模型。

## RAG 用小白语言怎么理解

RAG 就像开卷考试：模型本身像一个会组织语言的答题者，知识库像你允许它查阅的资料，检索器负责把最相关的几页递到桌上。

完整链路通常是：

```text
原始文档 → 清洗 → 分块 → 向量化 / 建索引 → 用户提问
                                      ↓
                    检索相关片段 → 重排 → 放入 Context
                                      ↓
                           模型回答 + 引用
```

## 为什么不能把所有文档直接塞进去

文档越长，成本、延迟和无关信息越多；模型还可能忽略位于中间的关键段落。分块就是把一本书拆成可以独立检索的小卡片。

分块时要考虑：

- 按标题、段落和语义切，不要只按固定字符数切；
- 保留文档名、章节、日期、权限等 metadata；
- 适度重叠，避免一句话刚好被切成两半；
- 不要把表格、代码和正文无脑混在一起。

## Embedding 和关键词检索

Embedding 可以把文字变成一串数字，使语义相近的内容在向量空间里更接近。它像把每张资料卡放到一张“意义地图”上。

但向量检索不是万能的。订单号、法规编号、产品型号这类精确字符串，关键词检索可能更好。实际系统常把关键词和向量检索结合，再进行 rerank。

| 查询类型 | 可能更有效的方式 |
| --- | --- |
| “如何申请年假” | 语义检索 |
| “制度 HR-2026-03” | 关键词 / 精确匹配 |
| “报销上限是多少且适用于实习生吗” | 混合检索 + 重排 |

## Citation 不是装饰

回答“可以报销”时，系统应该告诉用户：来自哪个文档、哪一节、哪一段。引用的价值是让用户能复核，也让团队发现检索错误。

至少保存这些信息：

```json
{
  "source": "员工报销制度.md",
  "section": "第三章 交通费",
  "chunk_id": "expense-003",
  "quote": "市内交通每次最高..."
}
```

如果模型写出的结论在引用里找不到，不要继续优化文案，而要把它标记为引用检查失败。

## 先做一个不用向量数据库的实验

为了理解链路，可以先写一个极简关键词检索：把文档按段落切开，统计查询词在每段出现的次数，返回得分最高的三段。

这个小实验虽然不“高级”，却能让你看见：导入什么、如何切块、如何排序、传给模型什么、引用从哪里来。理解后再换 Embedding 和 Vector DB，才不会只会调用框架。

## RAG 最常见的五类失败

1. **根本没检索到**：切块为空、索引失败、查询词不匹配；
2. **检索到了但不相关**：chunk 太大、metadata 缺失、问题需要改写；
3. **相关片段排在后面**：需要 rerank 或增加 top-k；
4. **资料过期或权限不对**：知识库更新和访问控制没有接上；
5. **检索正确但模型答错**：提示没有要求“只基于资料”，或没有做引用校验。

排查 RAG 时先单独打印检索结果，不要只看最终答案。你要知道模型到底看到了什么。

## 建立第一份评估集

从真实资料中写 20 个问题，每个问题记录：标准答案、必须包含的依据、不能说的内容、允许“不知道”的条件。然后比较不同 chunk、top-k 和 Prompt 的结果。

| 评估项 | 例子 |
| --- | --- |
| 检索命中 | 正确片段是否进入前 3 条 |
| 依据正确 | 引用是否真的支持结论 |
| 拒答正确 | 资料没有答案时是否承认不知道 |
| 完整性 | 是否遗漏条件和例外 |

## 本章动手项目

把 P1 文档助手升级为“课程资料问答助手”：支持导入 5 篇资料，回答问题时展示引用；资料没有答案时明确说“当前资料未找到”。保存每次检索结果，至少记录一次失败和修复过程。

## 本章验收

- 能解释分块、Embedding、检索、重排和 Citation；
- 能独立查看“模型实际拿到的检索片段”；
- 能区分检索错和生成错；
- 有至少 20 条评估问题；
- 能证明一次检索策略修改是否有效。

## 进一步小白练习

## 从三篇文档做出最小知识库

准备三篇短文：一篇有效制度、一篇旧制度、一篇与问题无关的说明。给每篇添加 metadata：文档名、生效日期、部门和权限。

### 第一步：导入

读取文件并按标题或段落切成小片段。每个片段都要带回来源信息，不能只保存一段孤立文字。

### 第二步：检索

先用关键词检索观察结果，再换向量检索。对同一个问题打印 top-3 片段和得分，确认旧制度是否被错误排在前面。

### 第三步：生成

只把相关片段交给模型，并要求：没有依据就拒答；每个结论带来源；如果多篇资料冲突，先指出冲突和日期。

### 第四步：评估

写 10 个问题，其中 3 个专门问旧制度、2 个问资料中不存在的内容。这样才能测试日期过滤和拒答能力。

## 用“检索日志”避免头晕

每次回答保存一条简化记录：

```text
问题：
命中的 chunk：
最相关的来源：
模型最终引用：
引用是否支持结论：是 / 否
失败属于：导入 / 分块 / 检索 / 生成 / 引用
```

如果你不记录检索结果，就像只看考试分数却不看答题过程，很难知道应该补哪一课。

## 本节练习

把一段 600 字文章分别切成 3 块和 10 块，比较检索结果。不要只看最终回答，先比较“送进模型的片段”。写下你认为更好的方案以及代价。
