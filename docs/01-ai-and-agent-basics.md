# 01｜AI 与 Agent 基础认知

> 💡 **提示**
> 先不背术语。我们从一个问题开始：如果用户给你一份材料，要求“读完后给结论、引用依据、必要时查系统并执行动作”，哪些部分应该交给模型，哪些部分必须由程序控制？

# 本章解决什么问题

本章建立一张足够工作的地图：模型负责生成与判断，程序负责约束与执行，外部数据负责提供依据，人工负责高风险决策。学完后你应能把“做个 Agent”改写成可设计、可测试的系统。

# 从真实任务引出概念

| 术语 | 它解决什么问题 | 日常类比 |
| --- | --- | --- |
| LLM | 根据上下文生成下一段文本或结构 | 像读过大量材料、反应很快的实习生，但不天然知道你公司的最新规则 |
| Token | 模型处理文本的计量单位，影响上下文容量和成本 | 像快递计费的重量单位；字越多，包裹越重，不等于内容越有价值 |
| Prompt | 告诉模型任务、角色、约束和输出要求 | 像给同事写任务单；只说“处理一下”通常会得到不同理解 |
| Context | 本次调用时模型实际看到的全部信息 | 像会议桌上的材料；没有放上桌的知识不能指望对方稳定使用 |
| Structured Output | 让输出符合字段和类型，便于程序继续处理 | 像把自由发挥的汇报改成固定表单，后续系统才能接住 |
| Multimodal | 同时处理文本、图片、音频或文件等输入 | 像同事不仅能读文字，也能看图纸、听录音 |
| Tool | 模型可以请求程序执行的具体能力 | 像实习生桌上的计算器、查询系统或发邮件按钮 |
| Workflow | 预先设计好的多步骤流程和分支 | 像报销审批流程，步骤清楚时不需要每一步临时决策 |
| RAG | 先从外部知识检索，再把相关片段放进 Context | 像开卷考试，先翻到相关页再作答；不是把整本书硬塞进脑子 |
| Agent | 围绕目标，根据状态和工具结果动态决定下一步 | 像会根据现场结果调整计划的项目助理，不是固定脚本的改名 |
| Memory | 跨轮次或跨任务保存的状态与信息 | 像项目记录本；记录什么、保留多久、谁能看都要有规则 |
| Skill | 一类可复用任务的做法、约束和资源包 | 像岗位 SOP 加模板，不等于某一次点击动作 |
| MCP | 让 AI 应用以标准化方式连接工具和数据 | 像统一规格的插座；能接上不等于自动拥有所有权限 |

# 最小必要理论：四层系统

| 层 | 核心问题 | 控制权 |
| --- | --- | --- |
| 模型层 | 生成、分类、提取、判断是否需要工具 | Prompt、模型选择、上下文和输出 schema |
| 应用层 | 数据如何流动、步骤如何执行、失败如何恢复 | Workflow、状态、重试、停止条件、人工确认 |
| 知识层 | 回答依据来自哪里，是否可追溯 | 数据源、检索、引用、版本和权限 |
| 交付层 | 谁能使用、出了问题如何发现、成本是否可接受 | 日志、Tracing、Evaluation、权限、安全和部署 |

# 极简案例：报销政策助手

用户问“这笔差旅费能报吗？”

1. 普通 LLM 调用：适合解释公开规则，但可能没有最新政策依据。
2. RAG：检索当前政策条款，把条款和版本放进上下文，并返回引用。
3. Workflow：先识别费用类型，再检索政策，再结构化判断，最后要求人工确认。
4. Agent：只有当任务需要根据查询结果决定是否继续查系统、补问用户或执行多个工具时才值得使用。

结论：不是越“智能”越好，而是让系统在可控范围内完成目标。

# 跟着做

1. 找一个熟悉场景，画出“用户输入 → 模型 → 数据 → 程序 → 人工”的数据流。
2. 为每个步骤标记：是否需要模型、是否需要外部数据、是否可能产生副作用。
3. 把任务分别改写成普通调用、Workflow、RAG 和 Agent 四个版本，比较复杂度、可控性和收益。

# AI Coding 学习方法

让 AI 解释概念时必须要求：先给真实问题，再给最小机制，最后给一个失败案例。让 AI 设计系统时必须要求它列出状态、工具输入输出、停止条件、权限边界和测试样例。

# 自己修改

- 把“万能知识助手”改成一个只回答“材料实验室设备预约规则”的助手。
- 为输出增加 evidence 字段，并规定没有依据时必须返回“无法确认”。
- 删掉一个你认为不必要的 Agent 步骤，用固定 Workflow 替代并说明原因。

# Debug 挑战

> 故意让助手回答一条知识库中不存在的问题。检查它是否编造答案、是否返回无依据的引用、是否把检索失败误报为“没有相关信息”。

排查顺序：输入是否进入上下文 → 检索是否命中 → 模型是否看到来源 → 输出 schema 是否校验 → UI 是否隐藏了错误。

# 小项目：AI 任务分流器

输入 10 条真实需求，把每条分为“普通调用 / Workflow / RAG / Agent / 不适合 AI”，输出选择理由、风险和最小验收指标。禁止只输出分类，不写理由。

# 验收标准

- 能解释 LLM、Prompt、Context、Tool、Workflow、RAG、Agent、Skill、MCP 的区别，并各举一个不用它的场景。
- 能画出一个任务的数据流，指出模型调用点、外部数据点和副作用点。
- 能判断“需要动态规划”是否真的足以支持 Agent，并说出更简单的替代方案。

# 自测与常见误区

- 为什么把更多文字塞进 Context 不一定更好？因为噪声、成本、延迟和冲突规则都会增加。
- 为什么 Tool Calling 不等于 Agent？工具只是能力，Agent 还需要目标、状态、决策循环和停止条件。
- 为什么 MCP 不等于权限？协议统一连接方式，但权限仍由服务端、用户身份和授权策略决定。
- 常见误区：把模型自信当事实；把 RAG 当数据库查询的自动替代；把 Agent 当固定流程的包装；把 Multi-Agent 当复杂度的免费消除器。
