> 先记住一句话：**模型负责生成和判断，程序负责约束和执行，外部资料负责提供依据，人负责承担高风险决策。**

## 先从一个真实请求开始

用户说：“请读完这份材料，告诉我重点；如果里面提到我的订单，就查一下订单状态，必要时帮我申请退款。”

这句话看起来像一个任务，实际上包含了多种工作：读材料、总结、查系统、判断是否符合退款规则、执行退款。它们不应该全部交给模型。

| 工作 | 更适合谁做 | 原因 |
| --- | --- | --- |
| 从文章中提炼可能的重点 | 模型 | 语言理解和归纳速度快 |
| 判断订单号格式是否正确 | 程序 | 规则明确，应该稳定一致 |
| 查询订单状态 | 工具 / 外部系统 | 数据在业务系统里，不在模型记忆里 |
| 判断是否满足退款政策 | Workflow + 资料 + 模型辅助 | 需要规则、依据和可解释结果 |
| 真正提交退款 | 程序执行，但先请用户确认 | 这是有后果的外部动作 |

## 这些术语到底是什么

### AI、模型和 LLM

AI 是大类，模型是其中一种可计算的能力，LLM 是擅长处理语言的模型。可以把 LLM 想成“读过大量材料、能够根据当前材料续写答案的助手”。

它不是数据库，也不是事实裁判。它会根据看到的内容生成最像答案的内容，因此可能说得很流畅但事实不对。

### Token

Token 是模型处理文字时使用的计量单位，可以粗略理解为“模型阅读和生成时的文字颗粒”。Token 越多，通常意味着上下文容量和费用越高，但不代表答案一定更好。

类比快递：重量会影响运费和车厢容量，但包裹更重不等于里面的东西更有价值。

### Prompt 与 Context

Prompt 是你给模型的任务说明；Context 是模型这一次实际看到的全部信息，包括系统指令、用户问题、历史对话、检索资料和工具返回值。

“我明明告诉过它”常常是误会：如果那段信息没有放进本次请求的 Context，模型就不能稳定使用它。

### Workflow

Workflow 是你提前设计好的步骤和分支。例如：先提取订单号 → 查订单 → 判断状态 → 生成解释 → 等用户确认 → 执行动作。

它像机场安检流程：步骤是预先安排的，哪个条件不满足就走哪条固定分支。适合规则清楚、稳定性要求高的工作。

### Tool Calling

Tool Calling 不是模型自己去“连接一切”，而是模型输出一个结构化的工具请求，程序验证参数后真正调用函数或 API，再把结果交回模型。

类比餐厅：模型是服务员，负责理解“我要一份低糖饮料”；厨房和收银系统才是真正执行和记账的地方。

### RAG

RAG 的全称是 Retrieval-Augmented Generation，可以理解为“先查资料，再回答”。系统先从你的知识库找出相关片段，把片段放进 Context，模型再基于这些片段组织答案。

它不是给模型重新上课，也不能自动保证检索到的资料正确；检索质量、引用和评估仍然需要工程设计。

### Agent

Agent 通常是一个能够根据当前状态选择下一步行动的循环：观察 → 决定 → 调工具 → 读取结果 → 再决定，直到达到停止条件。

它像一个会自己安排工作的助理，但必须有边界：允许调用哪些工具、最多循环几次、哪些动作必须确认、失败后如何停止。

## 普通调用、Workflow、RAG 和 Agent 怎么选

| 需求特征 | 首选方案 | 示例 |
| --- | --- | --- |
| 输入输出简单，步骤一次完成 | 普通 LLM 调用 | 把一段文字改写成更清楚的说明 |
| 步骤固定，分支可以提前画出来 | Workflow | 先分类，再按类别走不同模板 |
| 需要依据内部资料回答 | RAG | 根据公司制度回答报销问题 |
| 下一步取决于工具结果，路径不固定 | Agent | 先查客户，再决定查订单还是查库存 |

最常见的错误是“只要复杂就用 Agent”。复杂不等于需要自主决策；能画成固定流程时，Workflow 往往更容易测试和维护。

## 小实验：观察 Context 的作用

请准备一段 300 字的文章，分别做三次请求：

1. 只说“请总结这篇文章”，不给文章内容；
2. 把文章完整放进 Context；
3. 只放文章中间的一段，再问全文结论。

记录三次结果的差别。你会发现模型的能力不是凭空存在的，它的答案高度依赖本次真正看到的材料。

## 本章动手练习

把下面的任务分别标记为“普通调用 / Workflow / RAG / Agent”，并写一句理由：

- 把会议纪要改成三条待办；
- 根据员工手册回答年假问题；
- 用户问“帮我找到最便宜且明天能到的机票”；
- 把一段商品介绍翻译成英文。

参考答案不是唯一的，但理由必须包含“步骤是否固定、是否需要外部资料、是否需要外部动作”。

## 进一步小白练习

## 用同一个任务理解四种方案

任务：用户上传一份产品说明书，问“这款产品适合儿童吗？”

- **普通调用**：把说明书和问题一起交给模型，适合一次性处理短材料。
- **RAG**：说明书很多、需要重复查询时，先建立资料索引，再检索相关段落。
- **Workflow**：如果必须先检查年龄限制、再检查禁用成分、最后生成结论，可以把步骤固定下来。
- **Agent**：如果系统需要先判断该查产品资料、法规还是订单，再根据工具结果决定下一步，才考虑 Agent。

同一个业务目标可以有不同方案。选择不是看哪个名词更先进，而是看资料规模、步骤是否固定、是否要调用外部系统，以及错误的代价。

## 把“模型很聪明”改成可检查的说法

不要说“模型理解了这份资料”，而要问：

1. 它这次看到了哪些文字？
2. 它有没有按照要求输出字段？
3. 结论能不能在材料里找到依据？
4. 如果材料没有答案，它会不会承认不知道？
5. 如果需要执行动作，程序有没有拦截和确认？

这五个问题会把抽象的 AI 能力变成工程检查点。你不需要一开始知道模型内部如何计算，只需要知道系统能否被观察和验证。

## 一个简单的系统分层图

```text
界面层：用户上传文件、提问、确认动作
应用层：编排步骤、校验输入、处理错误
模型层：理解文本、生成草稿、选择工具
数据层：文件、知识库、数据库和日志
外部动作：查询、发送、修改、审批
```

当回答错了，先判断是哪一层的问题。文件没有上传成功，不是 Prompt 问题；工具权限不足，也不是换模型就能解决。
