# 07.02｜小橙的完整过程：从一句话到能运行

## 本节目标

跟着小橙走完做第一个应用的六步，建立"从需求到产品"的整体感觉。

## 一句话结论

> 从一句话需求到能运行的应用，中间只有六步，每一步你都看得懂、都能验收。

## 展开讲

小橙是谁？一个不会编程、想做一个"文档学习助手"的普通人。

下面是她指挥开发型 Agent（Codex / Claude Code 都可以）做出第一个应用的全过程。

**你不需要每个词都懂。跟着走一遍，先把流程装进脑子。**

### 第一步：需求一句话

她只说了一句人话：

> 我想做一个工具：贴进去一段文字或一个文件，它给我摘要、3 个重点概念和原文依据。

这句话里已经藏了三样东西：

| 藏着的 | 具体是 |
|-|-|
| 输入 | 一段文字，或一个文件 |
| 输出 | 摘要 + 3 个概念 + 原文依据 |
| 给谁用 | 她自己，复习资料用 |

**一句话需求能开工，但 Agent 会猜。** 所以还要第二步。

### 第二步：把需求扩成功能清单（还是人话，不是代码）

| 项目 | 内容 |
|-|-|
| 输入 | 用户贴一段文字，或上传一个文本文件 |
| 输出 | ① 100 字摘要 ② 3 个关键概念（各配一句大白话） ③ 每项都标原文依据 |
| 成功标准 | 抽查 10 条依据，至少 9 条能在原文里找到 |
| 边界 | 只读用户给的内容；不联网；不删除、不覆盖任何文件 |

四行填完，Agent 就不用猜了。

### 第三步：写成一份完整任务书

小橙把上面四行合成一段话发给 Agent：

```text
请做一个"文档学习助手"小工具：用户粘贴文字或上传文件，
输出——100 字摘要、3 个关键概念（各配一句大白话）、每项标原文依据。
成功标准：抽查 10 条依据，至少 9 条能在原文中定位到。
边界：只读用户提供的内容，不联网，不删除或覆盖任何文件。
请先实现一个能运行的版本，再告诉我怎么试。
```

> 复制后把【】里的内容换成你的。最后那句很重要：它挡住"Agent 一上来写二十个文件、你不知从哪看"。

### 第四步：让 Agent 实现，你只看大意

Agent 会自己建文件、写代码、跑起来。它会生成类似这样的核心逻辑：

> 下面这段代码由 Agent 生成。你不需要会写，只需要看懂大意：读进文字 → 出摘要 → 出 3 个概念 → 出依据，然后拼起来返回。

```python
# 由 Agent 生成（阅读样例，你不需要会写）
def learn(text):
    summary = summarize(text)       # 生成摘要
    concepts = extract_3(text)      # 抽出 3 个概念
    evidence = find_lines(text)     # 找出原文依据
    return summary, concepts, evidence
```

四行，四个动作。这就是你那个应用的心脏。

> 它干活时会显示"改了哪些文件"。这份改动清单叫 diff，就是"改了什么"的对照。详见第 04 章。你不需要读懂每行，只要确认：**它没碰你任务书边界之外的东西。**

### 第五步：验收——先跑一个正常样例

小橙贴了一段 500 字的文章，看输出：

- 摘要是不是 100 字左右？
- 概念是不是正好 3 个、解释是不是大白话？
- 点开几条"依据"，回原文搜关键词，能不能找到？

三个问题，全都能用"是 / 不是"回答。这就是好的验收标准。

### 第六步：提修改，再验收

发现两个问题，她在同一对话里直接说：

```text
概念 2 的解释还是太术语；第 3 条依据我在原文里找不到，请再核对；
另外输入空内容时它直接报英文错误，请改成中文提示"请先粘贴内容"。
```

Agent 改完，她再跑一遍，直到通过。

**这就是"验收 → 纠错 → 再验收"的循环。** 和你前面练的完全一样，只是对象从一张表变成了一个应用。

### 六步一览

| 谁在干 | 哪几步 |
|-|-|
| 你 | 第 1、2、3、5、6 步 |
| Agent | 第 4 步 |

六步里，只有第 4 步是 Agent 在干活。剩下五步都是你。

## 照着做

把小橙这六步套到你自己身上，先在纸上走一遍：

| 步骤 | 你做什么 | 会看到什么 | 不对怎么办 |
|-|-|-|-|
| 1 | 写下你的需求，一句话 | 一句人话 | 说不清就先把"输入"和"输出"各写一个词 |
| 2 | 补出输入、输出、成功标准、边界 | 四行清单 | 成功标准写不出就写"抽查 N 条，至少 X 条对" |
| 3 | 合成一段任务书，末尾加"先给能跑的版本" | 一段可直接发的话 | 太长就砍到 5 行以内 |
| 4 | 发给开发型 Agent，看它的改动清单 | 它改了哪些文件 | 越界了就叫停，把边界再强调一遍 |
| 5 | 跑一个正常样例，逐条对成功标准 | 过 / 不过 | 不过就把具体问题原文复制给它 |
| 6 | 提修改，再跑一遍 | 一个更接近的版本 | 改两次还不对，就回第 2 步重写标准 |

第 4 步之后，别急着夸它。**先看改动清单，再看结果。**

## 常见错误

- **错误一：只给一句话就让它做。** Agent 会按自己的理解猜，猜出来的多半不是你要的。
- **错误二：不写成功标准。** 没有"抽查 10 条依据 9 条可溯源"这类标准，你不知道算不算通过。
- **错误三：让它一次做完再给你看。** 加一句"先实现能运行的版本"，能省掉大量返工。
- **错误四：验收时只看输出好不好看。** 要按第二步那四行逐条对，一条一条打钩。
- **错误五：它改完你不重跑。** 每次改完都要重跑同一个样例，不然你不知道是真修好了还是碰巧。
