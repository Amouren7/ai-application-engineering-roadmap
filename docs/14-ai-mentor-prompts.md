# 14｜AI 导师 Prompt 库

> 好 Prompt 不只是“请帮我写代码”，而是让 AI 按正确的学习顺序帮助你：先澄清，再解释，再实现，再验证。

## 使用前的三个规则

- 不粘贴 API Key、密码、完整客户信息或公司机密；
- 先要求方案、假设和风险，再要求代码；
- 要求它给出验证方法，并自己运行和阅读结果。

## 需求澄清

```text
我想做：[一句话想法]
请不要写代码，先帮我澄清：用户、输入、输出、失败代价、权限、人工确认点和验收指标。
请指出你做了哪些假设，并给出一个最小可行版本。
```

## 小白解释术语

```text
请用完全没有编程经验的人能理解的方式解释：[术语]。
先用一句话，再用一个日常类比，再说明它在 AI 应用中的位置。
最后给我一个 10 分钟内能完成的小练习，不要引入额外框架。
```

## 阅读代码

```text
请先不要修改代码。
按“输入 → 处理 → 外部调用 → 输出 → 异常”的顺序解释这段代码。
指出我必须理解的 3 个变量和 2 个潜在风险。
```

## Debug

```text
现象：[准确描述]
复现命令：[命令]
输入：[脱敏后的最小输入]
完整错误：[错误]
最近改动：[改了什么]
请先列出最多 3 个假设，每个假设给一个验证步骤；不要直接重写全部代码。
```

## 方案评审

```text
请评审这个方案是否应该使用普通调用、Workflow、RAG 或 Agent。
从稳定性、可测试性、权限、成本、延迟和失败恢复六个角度说明理由。
请给出更简单的替代方案，并指出什么时候才值得升级。
```

## 测试与评估

```text
请根据这个功能生成 10 个测试样例：5 个正常、3 个边界、2 个失败。
每个样例写输入、期望行为、通过标准和可能暴露的问题。
不要把“模型回答看起来不错”当作唯一标准。
```

## 复盘

```text
项目目标：[目标]
最终结果：[结果]
失败案例：[案例]
请帮我区分需求问题、数据问题、Prompt 问题、程序问题和评估问题。
最后只给出下一步最重要的 3 个改进，不要扩展成万能重构。
```

AI 的回答是建议，不是验收结果。你仍然要运行测试、检查 diff、核对引用和确认权限。

## 进一步小白练习

## 让 AI 逐步提示，而不是直接给答案

```text
我正在学习：[主题]
请采用提示模式：先只给一个方向，不直接给完整答案。
等我回复尝试结果后，再指出一个具体错误和下一步。
如果我连续失败两次，再给出更明确的示例。
```

这比直接复制最终代码更适合建立能力。

## 让 AI 做评估员

```text
请根据以下标准评估结果：事实正确、引用支持、格式合格、拒答合理、用户易懂。
先逐项打分并引用证据，再给出最多三个改进建议。
不要因为语言流畅就默认事实正确。
```

## 让 AI 检查隐私和安全

```text
请只检查这段配置和代码中可能暴露的密钥、个人信息、越权调用和危险写入。
不要复述任何敏感值；用“已发现 / 未发现 / 无法判断”说明证据边界。
```

## 本节练习

同一个问题分别使用“直接回答模式、提示模式、评估模式”，比较哪一种最能帮助你真正理解。

## 第二轮小白练习

## 一次只让 AI 扮演一个角色

解释概念、写代码、做评估和做安全审查是不同任务。把它们混在一句 Prompt 里，AI 可能跳过解释直接给代码。你可以这样分轮：第一轮只澄清；第二轮只解释；第三轮只给最小改动；第四轮只给验证命令。

## 让 AI 先问你问题

```text
在提出方案前，请先问我最多 5 个必要问题。
如果信息不足，请明确标记“未知”，不要自行补充事实。
等我回答后，再给一个最小可行方案。
```

## 让 AI 做代码变更摘要

```text
请用表格列出本次修改的文件、行为变化、潜在风险和验证命令。
不要声称测试通过，除非你看到了实际测试输出。
```

## 本章最终产物

建立一个你自己的 Prompt 文件夹，按需求、解释、编码、Debug、评估、安全和复盘分类。每条 Prompt 都记录适用场景和一次实际效果。
