# 12｜常见错误与避坑指南

> Debug 的第一原则：先复现和分层，再修改。不要看到“回答不对”就立刻换模型或重写 Prompt。

## 一套通用排查顺序

```text
输入对吗？
  ↓
程序有没有读到？
  ↓
请求发出去了吗？状态码是什么？
  ↓
响应内容是什么？解析成功吗？
  ↓
检索 / 工具返回了什么？
  ↓
最终展示时有没有再次改坏？
```

每一步都打印安全的摘要和 request id，不要直接打印密钥或完整敏感原文。

## API 类错误

| 现象 | 常见原因 | 先做什么 |
| --- | --- | --- |
| 401 | 密钥错误、环境变量没加载、账户无权 | 打印变量是否存在，不打印值；确认当前账户 |
| 400 | 参数名、类型或 JSON 错误 | 查看原始请求和服务文档 |
| 429 | 限流或配额不足 | 读取服务端提示，限次重试 |
| 500 / 503 | 上游临时故障 | 记录 request id，稍后重试或降级 |
| 请求超时 | 网络、输入过长、工具慢 | 分别测量每一步耗时 |

## 回答不符合资料

先把检索片段单独输出：

- 没有片段：检索或索引问题；
- 有片段但不相关：分块、查询或排序问题；
- 片段相关但答案添加了内容：生成约束或引用检查问题；
- 资料本身过期：更新和权限治理问题。

“提高 temperature”通常不是解决事实错误的第一步。

## JSON 解析失败

保留原始响应，确认是模型输出了说明文字、字段缺失、类型不对，还是 SDK 取错字段。结构化输出需要三层保护：模型约束、程序解析、业务字段校验。

## Agent 无限循环

检查是否缺少：最大步数、重复工具检测、失败计数、完成判断和未知动作分支。先把循环次数降到 3，记录每轮 state，再决定怎么改。

## 工具重复写入

当写入请求超时，不能直接再写一次。先用业务查询确认动作是否已经发生；使用幂等键或 request id；对未知状态转人工处理。

## 密钥泄露

立即停止继续传播，撤销或轮换密钥，检查 Git 历史、日志和截图，使用 `.env.example` 替代真实值。不要只删除当前文件，因为历史提交可能仍然保留。

## 本章练习

故意制造三个故障并写一页复盘：空输入、JSON 字段缺失、工具超时。每个故障记录现象、复现步骤、根因、修复、验证和剩余限制。

## 进一步小白练习

## 具体排错食谱

### 现象：程序说“没有 API Key”

先确认当前终端是否能看到变量名，再确认启动程序的环境和设置变量的环境是否相同。只检查变量存在与否，不打印值。最后确认代码读取的变量名和你设置的完全一致。

### 现象：RAG 总是答“找不到”

依次检查：文件是否成功导入、分块数量是否大于 0、索引是否完成、查询是否为空、top-k 是否合理、权限过滤是否把结果全排除了。先打印命中的 chunk，再决定改 Prompt。

### 现象：Agent 每次都调用同一个工具

打印每一轮的 state 和工具参数，增加重复检测、最大步数和失败计数。不要先换更强模型，因为没有停止规则时更强的模型也可能循环。

### 现象：改了 Prompt 但无法判断是否变好

恢复固定评估集，保留旧版本结果，逐条比较事实、格式、引用和拒答。一次只改一个主要因素。

## 排错报告模板

```text
问题标题：
影响用户：
首次发现时间：
最小复现：
现象证据：
排除过的假设：
根因：
修复：
如何验证：
如何避免再次发生：
```

写完报告后，未来遇到类似问题就不必从零开始。

## 本节练习

让同伴只看你的排错报告，尝试复现问题。如果他无法复现，说明报告还缺输入、版本或环境信息。

## 第二轮小白练习

## 先做“证据包”，再请别人帮忙

向别人求助时，一次准备这六样东西：运行命令、当前目录、最小输入、完整报错、最近改动、你已经排除的可能性。不要只发一句“代码不能跑”。

证据包能让对方复现，也能防止你和对方讨论不同的问题。涉及模型时，再加上模型标识、输入长度、响应状态码和是否能解析 JSON；涉及 RAG 时，再加命中的 chunk；涉及 Agent 时，再加每一轮 state。

## 安全的排错顺序

开发阶段可以增加临时日志，但要先脱敏，验证后删除或降级日志级别。永远不要为了定位问题把真实密钥、完整客户资料或生产数据库直接复制到公开聊天里。

## 本章最终产物

完成三份排错报告，并把其中一个故障转成自动化测试。这样你不仅解决了今天的问题，还减少了它下次重新出现的概率。

## 第三轮小白练习

## 把排错变成决策树

遇到“答案不对”，先问：输入是否正确？如果不正确，修输入；如果正确，再问模型实际看到的 Context 是什么；如果 Context 不对，查检索或拼接；如果 Context 正确，再检查输出约束和业务校验。

遇到“动作不对”，先问：模型是否提出了正确工具？如果不正确，查工具描述和任务分流；如果正确，再问程序是否验证参数和权限；如果验证正确，最后查外部系统响应和幂等处理。

这个顺序可以避免“所有问题都改 Prompt”的习惯。

## 如何知道修复真的有效

修复前保留一个能复现的样例，修复后重新运行同一个样例，再运行一组不相关的回归样例。记录通过和失败数量。如果只在一个样例上变好，不能直接说问题已经解决。

## 本章验收

- 能写出一份包含复现步骤和根因的排错报告；
- 能把至少一个故障变成自动化测试；
- 能区分输入、检索、生成、工具和外部服务问题；
- 能在排错时保护密钥和敏感数据。
