# 04｜Tool Calling 与 Workflow`n`n> 💡 **提示**`n> 当模型只能“说”不能“做”，应用就需要工具。当任务步骤和分支可以提前确定时，优先用 Workflow；不要为了显得智能，把固定流程包装成 Agent。

# 本章解决什么问题

用户希望系统查库存、算报价、查询政策、创建工单或发送通知。让模型直接输出“请帮我查一下”无法产生真实动作；让模型自由执行又会带来参数错误、越权和重复副作用。本章学习如何把能力做成受约束的工具和可观测流程。

# 为什么需要这些技术

| 概念 | 解决的问题 | 日常类比 |
|-|-|-|
| Tool Calling | 模型请求程序调用一个有明确输入输出的能力 | 像实习生填写取数申请单，系统决定是否真的执行 |
| Schema | 约束工具名、参数类型、必填项和枚举值 | 像银行转账表单，字段错了就不应提交 |
| Workflow | 固定步骤、条件分支和人工确认可重复执行 | 像审批流，路径预先设计，责任边界清楚 |
| State | 保存任务在第几步、拿到什么结果、还缺什么输入 | 像快递物流记录，不靠记忆猜包裹走到哪里 |
| Human-in-the-loop | 在高风险或不可逆动作前让人确认 | 像付款前的二次确认，不把最终责任交给自动化 |

# 最小必要理论

1. 模型先返回工具名和参数；应用验证参数；只有验证通过后才执行工具。
2. 工具返回结果后，结果必须重新进入状态或上下文，再决定下一步。
3. 读操作和写操作分开；删除、付款、发消息、改权限等副作用必须有授权和确认。
4. 每个 Workflow 都要定义成功、失败、超时、重试、人工接管和最终停止条件。

# 极简案例：报销预审 Workflow

步骤固定为：接收票据文本 → 提取金额和日期 → 查询报销规则 → 判断是否缺资料 → 输出预审结果 → 超过风险阈值时人工确认。这里不需要 Agent 自由规划，因为路径和责任边界都可以预先写清。

```text
tool: search_policy
input: {category: string, date: string}
output: {matches: [], policy_version: string, citations: []}

tool: calculate_reimbursement
input: {amount: number, category: string, currency: string}
output: {eligible_amount: number, reason: string}

workflow state:
received -> extracted -> policy_checked -> needs_human? -> completed / failed
```

# 跟着做

1. 选一个可重复的业务流程，画出节点、输入、输出、分支和副作用。
2. 为每个工具写 schema、权限、超时、错误类型和幂等策略。
3. 先用假工具返回固定结果，测试状态流转，再连接真实 API。
4. 把模型决策和程序执行分开记录，给每次运行生成 run_id。
5. 在所有写操作前加人工确认，并测试拒绝、重复提交和超时。

# AI Coding 学习方法

要求 AI 先输出状态机和工具契约，再实现代码。审查时逐行追问：参数是谁校验的？模型能否直接触发副作用？重复执行会怎样？错误返回是否进入状态？每次只实现一个节点并运行对应测试。

# 自己修改

- 为 search_policy 增加 policy_version 和 effective_date，禁止使用过期政策。
- 把写入类工具改成 dry-run 和 execute 两阶段。
- 给 Workflow 增加人工拒绝分支，并让拒绝原因进入最终报告。
- 给每个工具增加超时和最大重试次数，说明哪些错误绝不重试。

# Debug 挑战

| 现象 | 排查重点 |
|-|-|
| 工具名正确但参数错误 | schema、类型校验、默认值和模型实际返回的参数 |
| 工具执行成功但模型没用结果 | 工具结果是否写回状态和上下文，角色或消息顺序是否正确 |
| 失败后无限重试 | 重试对象、次数、退避、错误可恢复性和停止条件 |
| 用户重复点击造成重复动作 | 幂等键、执行状态、确认步骤和服务端去重 |
| 不该自动执行却执行了 | 工具权限、风险等级、人工确认和默认拒绝策略 |

# 小项目：可审计的 Workflow 助手

选择报销预审、采购询价或实验室预约之一，完成至少 4 个节点、2 个分支、1 个人工确认和 1 个写操作 dry-run。交付状态图、工具 schema、5 条测试、run log 和一次故障复盘。

# 验收标准

- 能解释 Tool、Workflow、State、Schema 和 Human-in-the-loop 的关系。
- 能独立写出一个工具的输入、输出、权限、错误和幂等约束。
- 能让失败流程停在可解释状态，而不是吞掉异常或无限重试。
- 能判断一个需求为什么应使用固定 Workflow，而不是 Agent。
- 能在不使用框架的情况下重做最小“模型请求工具 → 程序执行 → 结果回传”链路。

# 自测与常见误区

- 为什么工具不能只定义函数名？因为没有 schema、权限和错误契约，模型和程序都无法稳定协作。
- 为什么读工具和写工具要分级？写工具会产生外部副作用，错误代价更高。
- 为什么重试前要判断幂等性？同一请求可能被重复扣款、建单或发消息。
- 常见误区：模型直接拿数据库连接；把 API 调用成功当成业务成功；没有 run_id；把所有异常都重试；没有人工接管。
