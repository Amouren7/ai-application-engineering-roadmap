# 06｜Agent Engineering`n`n> 🧠 **提示**`n> Agent 不是“模型 + 无限工具”，而是围绕目标运行的受约束决策循环。越能提前写清步骤，越应该用 Workflow；只有动态性带来真实收益时才引入 Agent。

# 本章解决什么问题

研究、客服、销售和运营任务常常需要补问、查不同来源、根据结果改变下一步。固定流程覆盖不了所有路径，但完全自由又难以控制。本章把 Agent 拆成可观察、可停止、可测试的工程系统。

# Agent 的最小组成

| 组件 | 工程问题 | 日常类比 |
|-|-|-|
| Goal | 什么结果算完成 | 旅行目的地，不是“到处走走” |
| State | 已经知道什么、做过什么、还缺什么 | 旅行行程和已买车票 |
| Tool | 可以调用哪些外部能力，权限是什么 | 地图、电话和支付工具 |
| Loop | 观察结果后如何决定下一步 | 到了路口看路况再选方向 |
| Stop Condition | 何时成功、失败、升级人工或强制停止 | 预算用完或到达目的地就不继续绕路 |
| Memory | 哪些信息跨轮次保留，谁能访问，多久过期 | 旅行笔记，不是什么都永久保存 |

# 最小必要理论

- Agent Loop 通常是：读取目标和状态 → 请求模型决定行动 → 校验行动 → 调用工具或回复 → 写回结果 → 判断停止。
- Planner / Executor 可以把“制定计划”和“执行步骤”分开，但拆分会增加通信、状态和失败成本。
- Memory 分为任务内状态、会话记忆和长期知识；不要把三者混成一个无限增长的历史。
- Retry 只对可恢复错误有效；每一次循环都必须有次数、时间、预算或风险上限。
- Multi-Agent 只有在角色边界、并行收益或权限隔离明确时才值得使用。

# 极简案例：科研资料调查 Agent

目标：围绕一个研究问题整理 5 篇论文。Agent 可以搜索、读取摘要、提取证据、发现缺口后继续搜索，最后生成带引用的报告。它必须有最大搜索次数、最大 Token 预算、来源去重规则和人工确认。

```text
while not stop:
  observation = read_state()
  decision = model(goal, observation, available_tools)
  action = validate(decision)
  if action is final_answer:
      stop = quality_check(action)
  elif action is tool_call:
      result = run_tool(action, timeout, permissions)
      state = append_result(state, result)
  elif action is ask_human:
      state = wait_for_human(state)
  else:
      stop = "invalid_action"
```

# AI Coding 学习方法

要求 AI 先写状态转移表和失败路径，再生成 loop。让它分别实现“模型决定”和“程序执行”，禁止把两者写在一个不可测试的大函数里。用 AI 做反例生成器：要求它构造越权、无限循环、重复写入和错误引用案例。

# 自己修改

- 增加总循环预算和单工具预算，超过任一上限就转人工。
- 把长期 Memory 改成显式用户确认后保存，并增加过期时间。
- 实现 planner / executor 两种版本，比较准确率、延迟、成本和故障恢复。
- 删掉一个 Agent 能力，用 Workflow 替代，并写出复杂度下降的证据。

# Debug 挑战

| 现象 | 排查重点 |
|-|-|
| 无限循环 | 停止条件、状态是否更新、工具结果是否被识别、循环预算 |
| Agent 重复调用同一工具 | 去重键、结果写回、幂等性、模型是否收到失败原因 |
| Agent 越权读取或执行 | 工具白名单、用户身份、参数过滤、服务端权限和人工确认 |
| 复杂度比收益大 | 对照固定 Workflow，比较成功率、成本、延迟和维护负担 |
| Memory 让回答越来越差 | 记忆选择、冲突信息、过期策略、隐私和上下文长度 |

# 小项目：专业 Agent

从科研、销售、客服、采购、运营或数据分析中选一个方向，完成一个单 Agent。必须有至少 2 个工具、1 个知识源、1 个人工确认、明确停止条件、失败转人工和运行轨迹。

# 验收标准

- 能解释 Agent 与固定 Workflow 的区别，并给出一个不应使用 Agent 的案例。
- 能写出最小 Agent Loop，增加工具、状态、重试和停止条件。
- 能排查工具调用失败、无限循环、越权和重复副作用。
- 能判断 Multi-Agent 的角色边界和并行收益，不把拆成多个角色当作自动变强。
- 能用一次对照实验说明 Agent 引入后的收益是否覆盖额外成本。

# 自测与常见误区

- 为什么 Agent 必须有 Stop Condition？没有停止条件，错误会变成成本、延迟或副作用。
- 为什么 Memory 不是“把全部聊天记录保存下来”？长期记忆需要选择、权限、过期和冲突处理。
- 为什么 Multi-Agent 不一定更好？通信、协调、上下文和调试成本会叠加。
- 常见误区：把 Agent 当 Prompt；没有预算上限；让模型直接执行写操作；没有轨迹；只展示成功 demo。
