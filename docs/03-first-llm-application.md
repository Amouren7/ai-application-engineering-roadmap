# 03｜构建第一个 LLM 应用

## 本章开始前：准备与产出

| 项目 | 说明 |
|-|-|
| Python | 需要；先会运行 02 章的小程序即可，不要求系统学完 Python |
| API Key | 工程路线需要；体验路线可用网页聊天工具完成同样的 Prompt 实验 |
| 安装软件 | 工程路线需要安装模型 SDK 或 HTTP 客户端；不要把 Key 写进代码 |
| 能否只用网页工具 | 可以先体验，但结构化输出和错误处理要回到 Python 验证 |
| 本章产出 | P1 文档分析助手的最小版本：文字输入、摘要、结构化结果和失败提示 |

先完成“一次成功调用”，再加入 JSON、文件和评估。每一步都保留输入、输出和错误信息，这些是你之后排错的证据。

> 本章的目标不是做出“最聪明”的应用，而是看懂一次模型调用完整经过了哪些环节。

## 先拆开一次调用

把模型 API 想成一个远程函数。你传入请求，服务返回响应：

```text
你的程序
  ↓ 发送模型、任务、上下文和输出要求
模型服务
  ↓ 返回文本或结构化结果
你的程序
  ↓ 校验、保存、展示、继续处理
用户
```

如果回答不对，问题可能出在四个地方：输入材料错了、指令不清楚、模型不适合、程序没有校验结果。不要只修改 Prompt。

## 第一个最小调用

下面是抽象示例。模型名称和 SDK 接口会变化，请以你实际使用的官方文档为准；重要的是理解数据流：

```python
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

response = client.responses.create(
    model="your-model",
    input="用三句话解释什么是结构化输出。",
)

print(response.output_text)
```

运行前准备：安装 SDK、设置环境变量、确认网络和账户权限。不要在代码里填写真实密钥，也不要把完整响应直接当成最终业务结果。

## 给模型一张清楚的任务单

一个初学者 Prompt 至少要说清楚五件事：角色、任务、材料、限制、输出格式。

```text
你是学习助理。
任务：从给定文章中提取三个关键概念。
材料：只使用“文章内容”中的信息，不要补充外部事实。
限制：每个概念不超过 50 字；如果找不到依据，写“原文没有说明”。
输出：概念名称、解释、原文依据。
文章内容：...
```

这像给同事写工单。只写“处理一下”时，每个人都会产生自己的理解；把验收写出来，结果才更稳定。

## 从文本到文档分析助手

我们先实现 P1 的最小版本：输入一段文字，输出摘要、关键概念和疑问。

### 第一步：先定义输出

```json
{
  "summary": "不超过 200 字的摘要",
  "concepts": [
    {"name": "概念名", "explanation": "小白能懂的解释"}
  ],
  "question": "读者可能还不明白的问题"
}
```

### 第二步：让模型按结构输出

“请输出 JSON”不等于一定会得到合法 JSON。你需要在请求中明确字段、类型、数量和缺失信息怎么处理，然后在程序里用 JSON 解析器校验。

```python
import json

raw = response.output_text
try:
    result = json.loads(raw)
except json.JSONDecodeError:
    raise ValueError("模型没有返回合法 JSON")

required = {"summary", "concepts", "question"}
if not required.issubset(result):
    raise ValueError("结果缺少必要字段")
```

### 第三步：加入文件输入

先只支持纯文本文件，避免一开始同时处理 PDF、扫描件、表格和图片。读取文件、限制长度、调用模型、保存 JSON，这四步先跑通，再增加能力。

```python
from pathlib import Path

text = Path("notes.txt").read_text(encoding="utf-8")
if not text.strip():
    raise ValueError("文件为空")
```

文件太长时不要盲目截断。你需要记录截断位置，或者下一章再学习分段和检索。

## 如何判断结果变好了

准备 5–10 篇你熟悉的短文，给每篇写出人工参考答案。每次修改 Prompt 或模型后，固定跑同一批样例，记录：

| 指标 | 怎么看 |
| --- | --- |
| 事实正确 | 有没有凭空添加原文没有的结论 |
| 覆盖完整 | 关键点是否遗漏 |
| 格式合格 | JSON 是否能被程序解析 |
| 可读性 | 小白能否理解 |
| 稳定性 | 同一输入多次结果是否差异过大 |

没有测试集时，你只能凭印象说“感觉更好了”。

## 常见错误

- **401 / unauthorized**：通常是密钥、账户或环境变量问题；先检查变量是否真的被当前进程读到。
- **模型返回空字符串**：检查响应字段是否取对，别把 SDK 不同版本的字段名混用。
- **JSON 解析失败**：查看原始输出，再优化结构化约束；不要只在字符串外面硬切大括号。
- **回答看似合理但不符合文章**：把“只使用给定材料”写进约束，并增加原文依据字段。
- **上下文太长**：记录输入长度，先减少无关说明，再学习分块和 RAG。

## 本章动手项目

完成一个命令行文档分析助手：

```text
python analyze.py notes.txt
```

它至少要做到：成功处理一篇文章；文件为空时提示；模型调用失败时给出可读错误；输出保存到 `result.json`；README 写清安装、配置、运行和一个示例结果。

## 本章验收

- 能画出一次模型调用的数据流；
- 能修改 Prompt 中的任务、限制和输出格式；
- 能在程序中校验模型返回的 JSON；
- 能用固定样例比较修改前后结果；
- 能解释为什么结构化输出不是“让模型随便输出 JSON”。

## 进一步小白练习

## 把一次请求拆成六个可观察点

调模型时建议记录以下信息（敏感内容要脱敏）：

1. 输入文件是否存在、长度是多少；
2. Prompt 模板使用了哪个版本；
3. 发送的模型和请求参数是什么；
4. HTTP 状态码、耗时和 request id；
5. 原始响应是否为空、是否能解析；
6. 最终结果通过了哪些字段和业务校验。

这样当用户说“今天突然不好用了”，你不会只能重新点一次运行，而是可以定位到底是文件、请求、响应还是解析发生了变化。

## Prompt 迭代示范

### V1：只要求总结

```text
请总结这篇文章。
```

问题是标准不清，摘要长短和重点都不稳定。

### V2：加入读者和边界

```text
请给准备考试的初学者总结文章，最多 200 字，只使用文章内容。
```

结果通常更聚焦，但仍然不容易被程序检查。

### V3：加入结构和缺失处理

```text
返回 summary、concepts、evidence 三个字段。
concepts 必须有 3 项；每项包含 name 和 explanation。
evidence 必须引用原文短句；找不到依据时写“未找到”。
```

每次只改一个因素，并用同一批样例比较，否则你不知道到底是哪项改动带来了变化。

## 什么时候该加 Context

如果模型需要参考用户提供的材料，就把材料作为明确的上下文区块：

```text
<任务>
...
</任务>
<文章>
...
</文章>
<输出要求>
...
</输出要求>
```

分隔符不能替代权限和事实校验，但能减少任务说明和原文混在一起造成的误解。

## 小白版测试表

准备四个输入：正常文章、空文件、只有标题的短文、超过长度限制的长文。对每个输入写“应该返回什么”，再运行程序。通过标准包括：不崩溃、错误可读、结构可解析、没有把缺失内容编造成事实。
