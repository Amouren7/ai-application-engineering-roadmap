# 03｜构建第一个 LLM 应用

> 🚀 **提示**
> 本章的成果不是“成功调用一次模型”，而是一个能处理文件、输出固定结构、暴露失败原因、可被测试和修改的文档分析助手。

# 本章解决什么问题

面对论文、合同、实验记录或会议纪要，人工阅读慢，直接让模型总结又可能遗漏、编造或输出无法被程序使用的文字。本章把 LLM API 变成 P1：基础 AI Application。

# 为什么需要这些能力

| 能力 | 没有它会怎样 | 本章出口 |
| --- | --- | --- |
| LLM API | 只能在聊天窗口里试，无法进入程序 | 能管理请求、响应、错误和成本 |
| Prompt / Context | 同一文件每次输出风格不同，约束不稳定 | 能把角色、任务、来源和限制写清 |
| Structured Output | 程序无法可靠读取模型回答 | 能让输出符合字段、类型和校验规则 |
| 文件输入 | 只能分析手工复制的短文本 | 能处理文本文件，并知道何时需要多模态输入 |
| Streaming | 用户长时间看不到反馈 | 能区分展示体验与最终结果完整性 |

# 最小必要理论

- **请求：**身份指令、用户输入、上下文、模型参数、工具或结构化输出约束。
- **响应：**文本或结构化结果、使用量、可能的工具请求、错误和元数据。
- **Context：**模型本次实际看到的内容；文件在本地不代表模型已经看到。
- **Token：**影响上下文容量、延迟和费用的处理单位；不要用字符数粗略替代真实使用量。
- **Structured Output：**让模型按 schema 产出，程序仍需校验，不能把 schema 当事实保证。
- **多模态：**输入可以是文本、图片、音频或文件，能力和限制依赖具体模型与 API。
- **Streaming：**适合逐步展示，但最终结果仍应在服务端或应用端完成校验和记录。

# 极简案例：论文摘要提取

输入一段论文文本，输出标题、研究问题、方法、关键发现、局限、证据片段和置信度。没有证据片段时，输出必须明确标记“未找到”，不能由模型补写。

```python
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
response = client.responses.create(
    model=os.environ["MODEL_NAME"],
    instructions="你是严谨的文献分析助手。只根据输入材料回答。",
    input=[{
        "role": "user",
        "content": [{
            "type": "input_text",
            "text": "请分析以下材料，并返回研究问题、方法、发现、局限和证据片段：\n\n" + source_text
        }]
    }]
)
print(response.output_text)
```

上面只是机制示意。正式实现必须依据当前模型 API 官方文档补上结构化输出 schema、输入长度控制、超时、错误处理、日志、测试和隐私策略。模型名、SDK 方法和参数属于生态内容，最后核验日期为 2026-09-05。

# 跟着做：P1 最小闭环

1. 确定文档类型和用户问题，不要一开始支持所有格式。
2. 把文件读取、文本清洗、模型调用、结果校验和展示拆成独立步骤。
3. 先实现普通文本输入，再增加结构化输出；每一步都保留原始输入和校验错误。
4. 为输出设计最小 schema：summary、key_points、evidence、uncertainties。
5. 加入空文件、超长文件、无证据、网络失败和模型返回异常五个测试样例。
6. 用 5–10 份真实但已脱敏的材料形成第一版测试集，记录人工参考答案。

# AI Coding 学习方法

先让 AI 给出模块边界和数据流，再逐模块实现。要求它解释每个 SDK 调用的输入输出、失败类型和官方文档位置。让 AI 生成代码后，自己先删掉一个不必要的抽象，再运行测试确认行为没有变化。

# 自己修改

- 把自由文本输出改成带 evidence 和 uncertainties 的结构化输出。
- 增加 request_id，在日志中记录输入长度、输出长度、耗时和失败类型，不记录敏感原文。
- 增加一个“无法从材料确认”的规则，并用一份反例文档测试它。
- 把 Prompt、schema 和模型配置分离成可版本化文件，记录一次变更原因。

# Debug 挑战

| 现象 | 排查顺序 |
| --- | --- |
| 认证失败 | 环境变量是否加载、身份是否正确、请求是否发到了预期端点；不要在日志打印密钥 |
| 输出为空 | 响应对象实际结构、是否只读取了错误字段、是否被 Streaming 处理逻辑吞掉 |
| JSON 无法解析 | 是否使用 schema、服务端返回是否被截断、程序是否在校验前直接解析 |
| 总结很流畅但不可靠 | 证据是否进入 Context、Prompt 是否允许编造、测试集是否包含反例 |
| 成本或延迟突然升高 | 输入长度、重复请求、重试、输出上限和是否误发整份文件 |

# 小项目：P1 文档分析助手

交付内容：一个可运行入口；README；脱敏示例文档；结构化结果；至少 5 条测试；3 个失败样例及修复记录；一次 Prompt 或 schema 版本对比；一次 AI 生成代码的人工 Review。

# 验收标准

- 能解释一次请求中哪些内容属于指令、用户输入和上下文，模型何时被调用。
- 能独立修改输出 schema，并让程序在不符合 schema 时明确失败。
- 能处理空输入、超长输入、网络失败、无证据和模型异常。
- 能用测试集比较修改前后结果，而不是凭一个好例子判断变好。
- 能不用教程重做“读取文本 → 调用 API → 校验结果 → 输出报告”的核心链路。

# 自测与常见误区

- 为什么 Prompt 写得更长不一定更好？因为优先级冲突、噪声、Token 成本和维护难度都会上升。
- 为什么 Structured Output 不能消除幻觉？它约束格式，不保证字段内容真实。
- 为什么 Streaming 不能替代最终校验？流式片段可能不完整，用户看到的内容也可能被中断。
- 常见误区：把 API key 写进代码；只测试成功样例；把模型回答当数据库；把超长原文全部塞进请求；不记录 Prompt 版本。
