# 13｜学习进度与打卡

> 打卡不是证明“我看过视频”，而是记录“我能交付什么证据”。

## 每次学习记录四行

```text
今天要解决的问题：
我实际做了什么：
遇到的失败和根因：
下一步最小行动：
```

不要写“学习 Python 2 小时”，改写成“完成文本统计 CLI；发现空文件会报错；下一步补输入校验”。后者才知道能力有没有增长。

## 8–12 周参考节奏

| 周次 | 主线 | 交付证据 |
| --- | --- | --- |
| 第 1 周 | L0–L1 | 命令行、Python、JSON、Git 小练习 |
| 第 2 周 | L2 | 第一次模型调用和 P1 原型 |
| 第 3 周 | L2 | 结构化输出、失败处理、测试样例 |
| 第 4 周 | L3 | Tool schema 和 Workflow |
| 第 5–6 周 | L4 | 知识库、检索、引用和评估集 |
| 第 7 周 | L5 | Agent Loop、状态和停止条件 |
| 第 8 周 | L6–L7 | 外部系统、权限、日志和成本 |
| 第 9–10 周 | L8 | P3 项目、部署、README 和演示 |

时间少就延长，不要为了赶日期跳过验收。

## 卡住时的三步协议

1. 把问题缩成一个最小可复现样例；
2. 记录完整报错和你已经尝试过什么；
3. 让 AI 先解释可能性和验证命令，不要直接要一大段重写代码。

如果 30 分钟仍没有进展，先写下当前证据，换一个更小的子问题。卡住本身也是工程记录。

## 阶段自测

每阶段都问：我能解释吗？能修改吗？能制造失败吗？能定位吗？能不用教程重做吗？如果只有“看懂”，就还没有到出口。

## 进一步小白练习

## 每周复盘卡

```text
本周完成的可运行成果：
我能解释的新概念：
我亲自修改过的代码：
一个失败样例：
失败根因：
本周最有效的学习方式：
下周唯一最重要的交付：
```

“亲自修改过的代码”很重要。它证明你不只是复制 AI 的输出，而是能够对实现做出判断。

## 能力等级不要靠感觉打分

给每项能力打证据分：0=没接触，1=看过示例，2=能照着做，3=能独立做，4=能解释并排查，5=能教给别人。只有 3 分以上才把它当作当前阶段的稳定能力。

## 低谷期怎么办

当连续几天没有进展，把任务降级成“读一个函数、运行一个样例、修一个错误”。不要同时换课程、换框架和换项目。稳定的小成果会帮你重新建立方向感。

## 本节练习

连续七天使用四行记录，周末只回看失败和下一步，不统计观看时长。

## 第二轮小白练习

## 用证据判断“我学会了吗”

以 L2 为例：

| 证据等级 | 你能做到什么 |
| --- | --- |
| 0 | 听说过模型 API |
| 1 | 跟着教程运行一次 |
| 2 | 能替换输入并得到结果 |
| 3 | 能独立写一个最小调用 |
| 4 | 能处理失败、校验输出和解释取舍 |
| 5 | 能教别人并设计评估集 |

只有达到 3，才算能做；达到 4，才算稳定；达到 5，才算可以把它教给别人。不要因为看完视频就给自己打满分。

## 一周学习安排示例

周一理解概念，周二照做最小例子，周三故意改坏，周四排错，周五加入自己的输入，周六整理 README，周日复盘和休息。每天都不必很长，但要有一个可查看的结果。

## 本章最终产物

一份起点卡、四周学习记录、每阶段证据清单、至少三个失败样例和下一阶段唯一目标。进度记录的作用是减少迷茫，不是制造压力。
