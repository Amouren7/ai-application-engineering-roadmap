# 08｜生产级 AI 应用工程

> 🏭 **提示**
> 生产级不是“部署到云端”四个字，而是系统在真实用户、真实权限、真实失败和真实成本下仍然可解释、可控制、可恢复。

# 本章解决什么问题

Demo 可以回答一个问题，不代表系统值得交付。生产环境会遇到输入变化、模型漂移、服务限流、隐私风险、成本失控、延迟过高和用户误操作。本章建立从测试集到上线、监控、回滚和持续优化的闭环。

# 生产级能力地图

| 能力 | 必须回答的问题 | 最小证据 |
| --- | --- | --- |
| Evaluation | 结果是否真的变好 | 版本化测试集、指标、人工抽检和前后对比 |
| Tracing / Observability | 一次请求经过了什么、慢在哪里、错在哪里 | run_id、span、模型调用、工具调用、耗时和错误 |
| 错误处理 | 失败后用户看到什么，系统如何恢复 | 分类错误、重试、降级、人工接管和告警 |
| 缓存与成本 | 能否减少重复计算并控制 Token / API 费用 | 缓存 key、命中率、Token、单次成本和预算 |
| 权限与隐私 | 谁能看什么、数据保留多久、谁能执行副作用 | 权限矩阵、脱敏、保留策略和审计记录 |
| 部署与回滚 | 如何发布、发现问题、恢复上一版本 | 环境配置、健康检查、版本号、发布和回滚步骤 |

# 最小必要理论

- 测试集评估行为，日志解释运行，Tracing 连接一次运行中的各个步骤；三者不能互相替代。
- Prompt、schema、模型、检索策略和工具版本都要可追踪；否则无法解释一次变化。
- 延迟预算要拆成排队、网络、模型、检索、工具和展示时间；总耗时不是唯一指标。
- 缓存必须绑定输入、Prompt、模型、知识版本、权限和工具结果，防止脏数据或越权复用。
- 安全边界包含输入、输出、工具参数、数据访问、日志、依赖和部署环境。

# 极简案例：把 P2 变成可交付服务

企业知识助手上线前，先冻结一版测试集和知识版本，配置每次运行的 run_id，记录检索片段、引用、耗时、Token 和错误。对无依据问题拒答，对权限不足问题不泄露资源存在性，对高风险写操作转人工。

| 层级 | 失败处理 |
| --- | --- |
| 输入层 | 格式、长度、敏感字段和恶意指令校验 |
| 模型层 | 超时、限流、空响应、内容安全和输出 schema 校验 |
| 知识层 | 索引缺失、版本冲突、无命中、权限不足和引用不支持 |
| 工具层 | 参数错误、授权失败、重复副作用、外部系统异常 |
| 交付层 | 告警、降级、人工接管、版本回滚和事故复盘 |

# 跟着做：上线前闭环

1. 建立最小测试集：正常、边界、无答案、冲突、越权、恶意输入和工具失败。
2. 给 Prompt、schema、模型、检索和工具建立版本标识。
3. 为每次运行记录 run_id、用户级别、步骤、耗时、Token、成本、结果和错误类型。
4. 定义 SLO 或预算：成功率、引用准确率、P95 延迟、单次成本、人工接管率。
5. 实现超时、指数退避、有限重试、降级回答、人工接管和告警。
6. 进行隐私和安全检查：密钥、日志、输入注入、越权、依赖、数据保留和删除。
7. 用灰度或小范围用户发布，比较新旧版本，保留一键回滚路径。

# AI Coding 学习方法

让 AI 先生成生产检查清单和故障演练矩阵，不要先生成部署脚本。要求它解释每个监控指标对应的用户风险，审查所有默认配置、网络暴露、密钥来源、权限和日志。对部署代码使用最小权限和可回滚提交。

# 自己修改

- 给 P2 增加 P95 延迟、单次成本和人工接管率三个指标。
- 将缓存 key 增加权限范围和知识版本，写一个越权缓存测试。
- 增加一个模型或 Prompt 版本，使用同一测试集比较新旧结果。
- 模拟模型超时、索引损坏、外部 API 403 和日志系统不可用，验证系统是否仍可解释地失败。

# Debug 挑战

| 现象 | 排查重点 |
| --- | --- |
| 准确率下降 | 测试集是否变化、Prompt、模型、知识版本、检索、schema 和人工判定 |
| 延迟升高 | 各 span 耗时、排队、重试、输入长度、检索和外部工具 |
| 成本失控 | Token、重复请求、缓存命中率、循环次数、模型路由和输出长度 |
| 用户看到敏感数据 | 权限过滤、缓存 key、引用、日志、错误回显和第三方服务 |
| 发布后无法回滚 | 版本是否不可变、配置是否记录、数据库迁移和部署产物是否可复现 |

# 小项目：生产发布包

把 P2 或 P3 打磨成可交付版本。交付 README、架构图、部署步骤、环境变量清单、测试集、评估报告、Tracing 样例、成本和延迟报告、权限矩阵、故障演练记录、隐私说明、版本记录和回滚说明。

# 验收标准

- 能区分 Evaluation、Logging、Tracing、Monitoring 和用户反馈的职责。
- 能用数据说明一次优化是否改善了正确率、引用、延迟、成本或人工接管。
- 能排查模型、检索、工具、权限、缓存和部署各层故障。
- 能设计默认拒绝、高风险人工确认、有限重试、降级和回滚。
- 能把一次线上问题复盘成可复现测试，并推动版本改进。

# 自测与常见误区

- 为什么“用户说好用”不等于 Evaluation 通过？反馈有价值，但还需要可重复的测试和指标。
- 为什么日志和 Tracing 都需要？日志适合事件记录，Tracing 适合一次请求跨步骤的因果链。
- 为什么缓存可能造成安全问题？如果忽略用户、权限或知识版本，缓存会复用错误或越权结果。
- 常见误区：只看平均延迟；只监控 HTTP 200；上线后才建测试集；把重试次数设很大；没有回滚和事故演练。
