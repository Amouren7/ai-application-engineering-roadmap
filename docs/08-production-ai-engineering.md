# 08｜生产级 AI 应用工程

> Demo 的标准是“能演示”；生产系统的标准是“出问题时知道、出了问题能停、恢复后能证明变好了”。

## 生产级到底多了什么

一个本地脚本可能只有“输入 → 模型 → 输出”。上线后，你还要回答：谁在调用、调用了几次、花了多少钱、延迟多久、失败在哪里、数据是否泄露、如何回滚。

可以把生产能力分成五层：

| 层 | 要回答的问题 |
|-|-|
| 质量 | 答案正确吗？引用可靠吗？ |
| 可观测 | 出错时能定位哪一步吗？ |
| 安全 | 谁能看、谁能改、密钥会泄露吗？ |
| 成本与性能 | 慢在哪里？贵在哪里？ |
| 发布与恢复 | 新版本坏了能退回去吗？ |

## Evaluation：不要只看感觉

建立一份固定评估集，按真实用户任务覆盖成功、边界和失败样例。每次换 Prompt、模型、检索策略或工具，都重新运行。

推荐记录：

```text
case_id：case-001
输入：用户问题和相关材料
期望：必须包含的结论 / 引用 / 拒答条件
实际：系统输出
结果：pass / fail
原因：检索错、生成错、格式错、工具错、人工标准不清
版本：prompt-v3 + model-x + retriever-v2
```

不要把“模型评分 8 分”当成唯一证据。人工抽查、规则检查和真实用户反馈应该互相补充。

## Logging 与 Tracing

日志回答“发生了什么”，Tracing 回答“一次请求经过了哪些步骤”。每个请求至少应该有一个 request id，串起：

```text
request_id
  ├─ 输入大小和类型
  ├─ Prompt / 模型版本标识
  ├─ 检索 query 和命中的 chunk id
  ├─ 工具名、耗时、结果状态
  ├─ token / 成本估算
  └─ 最终状态：成功、拒答、转人工、失败
```

不要把 API Key、完整身份证号、密码或不必要的原文直接写入日志。日志不是“什么都保存”。

## 延迟、成本和缓存

用户感受到的耗时可能来自：排队、模型调用、检索、工具接口和前端渲染。先分别测量，再优化。

- 固定的系统说明可以缓存；
- 相同的只读检索可以短期缓存；
- 写入动作不能只靠缓存结果；
- 降低 token 之前先确认没有删掉必要上下文；
- 复杂 Agent 要记录每一轮，而不是只统计总耗时。

优化必须有前后对比：延迟下降多少、成本下降多少、质量是否受损。

## Guardrail 和权限

Guardrail 可以是输入过滤、输出检查、工具白名单、金额上限、域名限制和人工审批。它不是一句“请遵守安全规则”，而是可以被程序验证的限制。

例如：

```text
模型可以提出“发送邮件”
程序检查收件人是否在允许域名
程序展示主题、正文和附件预览
用户确认后才真正发送
```

## 发布和回滚

把 Prompt、模型配置、检索参数和代码当作一个版本。发布前保留旧版本，出现质量或安全问题时能切回去。

最小发布清单：

1. 跑固定评估集；
2. 检查密钥和敏感日志；
3. 检查新权限是否超出原范围；
4. 先小范围试运行；
5. 记录版本、日期、影响章节和回滚方法。

## 故障演练

故意制造三个问题：模型超时、检索为空、工具返回 500。对每个问题写出用户看到的提示、日志应该出现什么、系统是否重试、什么时候转人工。

如果你只能说“让用户刷新”，说明系统还没有真正的故障处理设计。

## 本章验收

- 有一份可重复运行的评估集；
- 每次请求能追踪主要步骤；
- 日志不泄露密钥和不必要的敏感数据；
- 能测量一次调用的延迟与成本；
- 写入动作有权限边界、确认点和回滚思路。
