# 07｜Skill / MCP / 外部系统集成

> 这一章最重要的不是背缩写，而是知道“能力放在哪里、谁能调用、调用会产生什么影响”。

## 四个概念先分开

| 名称 | 小白版解释 | 例子 |
|-|-|-|
| API | 一个系统对外提供的接口 | GitHub 创建 issue 的接口 |
| Tool | Agent 可以调用的一次具体动作 | `get_order_status` |
| Skill | 一套可复用的做事说明、规则或流程 | “按规范检查一个 PR” |
| MCP | 让模型客户端用统一方式发现和调用外部工具 / 资源的连接协议 | 连接文件、数据库或 SaaS |

API 是门，Tool 是门后的一项动作，Skill 是说明书，MCP 是让不同客户端能按共同规则找到门和动作的协议。

不要因为接入了 MCP 就自动拥有权限。协议只解决连接方式，身份、授权、审计和安全仍由外部系统决定。

## 连接外部系统前先画边界

```text
用户意图
  ↓
模型 / Agent
  ↓ 选择一个已登记工具
权限检查与参数校验
  ↓
外部系统 API
  ↓
结果脱敏、记录、返回
```

任何一层都可能拒绝请求。尤其要把“读取”和“写入”分开：读日历和删除日历不是同一级权限。

## 最小权限原则

给一个 Agent 接 GitHub 时，先问：它只需要读仓库，还是要创建 issue？是否需要合并 PR？能不能限制到一个仓库？凭据泄露后损失多大？

建议按下面顺序授权：

1. 只读；
2. 指定仓库 / 指定资源；
3. 单一写入动作；
4. 写入前人工确认；
5. 有日志、撤销和恢复办法后再扩大范围。

“为了方便先给全部权限”会让后续排查和风险控制都变困难。

## Skill 应该写什么

一份好的 Skill 不是一句“帮我处理 GitHub”，而应该包含：

- 适用场景和不适用场景；
- 输入、输出和必需字段；
- 允许调用的工具；
- 高风险动作前的确认点；
- 失败时如何停止；
- 如何验证结果。

它像给新同事的操作手册：不仅告诉他怎么做，也告诉他什么时候不能做。

## MCP 连接的安全检查表

第一次连接一个 MCP 服务时，先不要让 Agent 自动执行：

- 服务来自哪里，是否是可信来源；
- 会暴露哪些文件、消息、数据库表；
- 工具描述是否可能诱导越权；
- 是否支持只读模式；
- 凭据保存在哪里，日志会不会记录敏感信息；
- 调用失败是否会重复写入。

工具描述也是输入，不要把工具返回的任意文字当作系统指令。

## 小练习：设计一个飞书资料查询工具

工具名：`search_learning_docs`

请写清楚：

```text
用途：只在学习路线文档中搜索关键词
输入：keyword，最多 50 个字符
输出：标题、来源链接、匹配片段
权限：只读，不修改文档
失败：搜索服务不可用时返回“暂时无法查询”
限制：不返回用户无权访问的内容
```

然后再设计一个“编辑文档”工具，比较两者在授权、确认和日志上的不同。

## 本章动手项目

为你的 P2 或 P3 项目接入一个外部系统，但只做一个最小连接：例如读取 GitHub issue、读取飞书文档、查询数据库中的一张表。先实现只读，再写一份风险说明，最后决定是否需要写入能力。
