# 07｜Skill / MCP / 外部系统集成

> 🔌 **提示**
> 问题先于协议：如果 Agent 需要连接飞书、GitHub、数据库或企业 CRM，怎样让它可发现、可授权、可审计、可撤销？MCP 是连接方式，不是权限的替代品。

# 本章解决什么问题

一个独立 Agent 很快会遇到真实世界：资料在飞书，代码在 GitHub，客户在 CRM，数据在数据库。把每个系统硬编码进 Prompt 难以复用，也容易把权限和副作用藏起来。本章学习可复用能力包、工具契约和标准化连接。

# 先分清四个概念

| 概念 | 它是什么 | 日常类比 |
| --- | --- | --- |
| Skill | 完成一类任务的说明、约束、资源和流程，可复用 | 岗位 SOP 加模板和检查清单 |
| Tool | AI 可以请求调用的一项具体外部能力 | 查库存按钮、计算器或发消息按钮 |
| MCP | 让 AI 应用和外部工具、资源以统一方式连接的协议 | 统一规格的插座和插头 |
| 外部系统 | 真正保存数据或产生副作用的服务 | 仓库、财务系统、CRM 或企业档案室 |

判断顺序：先确认任务和权限，再决定是否需要 Tool；工具多、连接方多或需要标准化发现时，再评估 MCP；重复出现的流程、约束和资料，才沉淀成 Skill。

# 最小必要理论

- 连接分为资源读取、工具调用和提示模板等能力；每一类都要有清晰的输入输出和权限。
- 认证回答“你是谁”，授权回答“你能做什么”；两者都不能只由模型自行决定。
- 最小权限、默认拒绝、显式确认、审计日志和可撤销授权是外部接入的基本安全线。
- 外部系统可能超时、限流、返回脏数据或改变 schema；应用必须做超时、校验、重试和降级。
- 不要把所有工具暴露给 Agent；按任务、用户、环境和风险动态提供白名单。

# 极简案例：飞书科研资料助手

目标：用户询问某个实验项目，Agent 读取飞书知识库中的允许范围，整理来源并生成摘要；若要创建任务或发送消息，必须先展示动作和参数，等待用户确认。读取、写入和分享是三个不同的风险级别。

| 动作 | 默认策略 | 记录内容 |
| --- | --- | --- |
| 读取公开资料 | 允许，但按用户身份过滤 | 用户、资源、时间、查询和来源 |
| 读取受限资料 | 依赖外部系统授权，失败则拒绝 | 授权范围、拒绝原因和 request_id |
| 创建任务 / 发送消息 | 展示预览，用户确认后执行 | 工具、参数摘要、确认人和结果 |
| 改权限 / 删除内容 | 默认禁止或转人工审批 | 完整审计、审批记录和回滚方案 |

# 跟着做

1. 选飞书、GitHub、数据库或一个 SaaS 作为连接对象，先读其官方开放平台文档。
2. 为只读、写入、分享、改权限分别列出工具和风险等级。
3. 先实现 mock connector，验证 schema、错误、权限和日志，再连接真实账号。
4. 为每个连接定义身份、授权范围、数据最小化、超时、限流、重试和撤销方式。
5. 把常用任务整理成 Skill，但把环境密钥和用户权限留在运行时配置。
6. 用一个成功、一个权限不足、一个过期授权、一个重复写入和一个服务超时测试。

# AI Coding 学习方法

让 AI 先画“模型 → MCP 客户端 → 服务端 → 外部系统”的边界图，再写工具契约。要求它列出所有副作用、敏感字段、授权点和审计字段。不要让 AI 为了“方便”把管理员令牌、全量数据或绕过确认的开关写进代码。

# 自己修改

- 把一个读写混合工具拆成只读工具、dry-run 工具和 execute 工具。
- 为每次调用增加 tenant_id、user_id、resource_id、scope、run_id 和结果摘要。
- 为敏感字段加入脱敏和字段级允许列表，验证日志不能还原原文。
- 把连接从真实服务切回 mock，证明核心 Agent 逻辑不依赖某个平台 UI。

# Debug 挑战

| 现象 | 排查重点 |
| --- | --- |
| 连接成功但资源为空 | 身份、授权范围、租户、资源归属和是否误用 bot 视角 |
| 偶发 401 / 403 | token 过期、scope、用户身份、服务端权限和缓存 |
| Agent 传入危险参数 | schema、枚举、资源范围、服务端校验和人工确认 |
| 写操作重复执行 | 幂等键、执行状态、重试策略和外部系统去重 |
| 敏感信息出现在日志 | 日志字段白名单、脱敏顺序、异常堆栈和第三方追踪配置 |

# 小项目：可撤销的外部系统连接器

完成一个飞书或 GitHub 连接器，并接入第 06 章的专业 Agent。交付连接架构图、Tool schema、Skill 说明、权限矩阵、mock 测试、人工确认、审计日志和撤销说明。至少一个写操作必须默认 dry-run。

# 验收标准

- 能用真实问题解释 Skill、Tool、MCP 和外部系统的边界。
- 能区分认证、授权、权限过滤、人工确认和审计。
- 能在 mock 环境独立测试连接器，不依赖某个平台当前 UI。
- 能排查过期 token、缺 scope、错误身份、越权参数和重复副作用。
- 能说明为什么“接上 MCP”不等于“安全地接入企业系统”。

# 自测与常见误区

- 什么时候只需要 Tool，不需要 MCP？只有一个应用、少量稳定工具且没有标准化连接需求时。
- 什么时候 Skill 比 Tool 更合适？当复用的是做事方法、约束和检查清单，而不是一个动作。
- 为什么权限不能放在 Prompt 里？Prompt 是可变文本，不能替代服务端授权。
- 常见误区：把 MCP 当万能插件市场；暴露全量工具；共享管理员 token；日志记录完整业务数据；没有撤销和回滚。
