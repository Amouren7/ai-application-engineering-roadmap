# 07｜Skill / MCP / 外部系统集成

> 这一章最重要的不是背缩写，而是知道“能力放在哪里、谁能调用、调用会产生什么影响”。

## 四个概念先分开

| 名称 | 小白版解释 | 例子 |
| --- | --- | --- |
| API | 一个系统对外提供的接口 | GitHub 创建 issue 的接口 |
| Tool | Agent 可以调用的一次具体动作 | `get_order_status` |
| Skill | 一套可复用的做事说明、规则或流程 | “按规范检查一个 PR” |
| MCP | 让模型客户端用统一方式发现和调用外部工具 / 资源的连接协议 | 连接文件、数据库或 SaaS |

API 是门，Tool 是门后的一项动作，Skill 是说明书，MCP 是让不同客户端能按共同规则找到门和动作的协议。

不要因为接入了 MCP 就自动拥有权限。协议只解决连接方式，身份、授权、审计和安全仍由外部系统决定。

## 连接外部系统前先画边界

```text
用户意图
  ↓
模型 / Agent
  ↓ 选择一个已登记工具
权限检查与参数校验
  ↓
外部系统 API
  ↓
结果脱敏、记录、返回
```

任何一层都可能拒绝请求。尤其要把“读取”和“写入”分开：读日历和删除日历不是同一级权限。

## 最小权限原则

给一个 Agent 接 GitHub 时，先问：它只需要读仓库，还是要创建 issue？是否需要合并 PR？能不能限制到一个仓库？凭据泄露后损失多大？

建议按下面顺序授权：

1. 只读；
2. 指定仓库 / 指定资源；
3. 单一写入动作；
4. 写入前人工确认；
5. 有日志、撤销和恢复办法后再扩大范围。

“为了方便先给全部权限”会让后续排查和风险控制都变困难。

## Skill 应该写什么

一份好的 Skill 不是一句“帮我处理 GitHub”，而应该包含：

- 适用场景和不适用场景；
- 输入、输出和必需字段；
- 允许调用的工具；
- 高风险动作前的确认点；
- 失败时如何停止；
- 如何验证结果。

它像给新同事的操作手册：不仅告诉他怎么做，也告诉他什么时候不能做。

## MCP 连接的安全检查表

第一次连接一个 MCP 服务时，先不要让 Agent 自动执行：

- 服务来自哪里，是否是可信来源；
- 会暴露哪些文件、消息、数据库表；
- 工具描述是否可能诱导越权；
- 是否支持只读模式；
- 凭据保存在哪里，日志会不会记录敏感信息；
- 调用失败是否会重复写入。

工具描述也是输入，不要把工具返回的任意文字当作系统指令。

## 小练习：设计一个飞书资料查询工具

工具名：`search_learning_docs`

请写清楚：

```text
用途：只在学习路线文档中搜索关键词
输入：keyword，最多 50 个字符
输出：标题、来源链接、匹配片段
权限：只读，不修改文档
失败：搜索服务不可用时返回“暂时无法查询”
限制：不返回用户无权访问的内容
```

然后再设计一个“编辑文档”工具，比较两者在授权、确认和日志上的不同。

## 进一步小白练习

## 用 GitHub 只读集成做一次练习

目标：让系统读取一个仓库最近的 issue，并按标签分类。第一版只允许读取，不创建、修改或关闭 issue。

实施顺序：

1. 在外部系统创建最小只读凭据；
2. 把“列出 issue”封装成一个工具；
3. 对仓库名、页码和数量做参数限制；
4. 记录调用时间、状态和结果数量；
5. 凭据失效时只返回可读错误，不把密钥打印出来；
6. 通过测试后再考虑是否需要写入能力。

## 连接说明书模板

```text
服务名称：
数据范围：
只读工具：
写入工具：
最小权限：
敏感字段：
失败处理：
是否需要人工确认：
撤销权限的方法：
```

把这张表写完，通常能发现自己还不知道系统到底会接触哪些数据。

## 外部系统的三个边界

- **身份边界**：工具代表谁调用，不能把用户身份和机器人身份混淆；
- **资源边界**：允许访问哪个仓库、文件夹、表或文档；
- **动作边界**：能读取、创建、修改还是删除。

MCP、SDK 或插件都不能替你回答这三个问题。

## 第二轮小白练习

## 从“能调用”到“敢交付”

外部连接的学习顺序建议固定为：假数据 → 本地模拟函数 → 真实只读 API → 真实写入预览 → 小范围写入。每一步都留下日志和撤销办法。不要一上来就把真实生产账号交给 Agent。

例如接入 GitHub，先用一个假函数返回三条 issue，验证模型能否按标签分类；再接真实 API，验证权限和分页；最后才讨论创建 issue。这样 API 故障、模型分类错误和权限问题不会同时出现。

## 如何判断一个连接值得接入

问四个问题：用户是否真的需要？手工完成有多麻烦？失败的代价是什么？能否用更简单的导出文件或人工流程替代？如果只是为了展示 MCP，而没有真实任务，先不要增加连接。

## 本章最终产物

你应该交付一张集成说明卡、一个只读工具、三种失败样例和一份权限撤销说明。别人拿到这四样东西，才有可能安全地复用你的集成。
