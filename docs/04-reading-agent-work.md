# 04｜看懂 Agent 干活：过程、diff 与确认点

> 本章目标：你从"下完任务就干等结果"，升级到"能看懂它一路干了什么、改了什么，并在关键动作前决定放行还是喊停"。

## 本章开始前：准备与产出

| 项目 | 说明 |
|-|-|
| 账号要求 | 一个能"读写文件、分多步干活"的 Agent 工具（办公综合型或开发型；纯问答型看不到改动清单） |
| 能否只用手机完成 | 部分可以；看改动清单和过程记录建议用电脑，屏幕大看得清 |
| 主线要不要写代码 | 不需要。本章的代码片段只作"阅读样例"，看懂大意即可 |
| 本章产出 | 一次"看痕迹 → 读改动清单 → 决定放行或喊停"的练习记录 |

## Agent 干活会留下痕迹

**结论一句话：Agent 不是"黑盒"，它每干一步都会留下痕迹；读懂这些痕迹，是后面验收的地基。**

你把任务交给 Agent 后，别急着盯"最终结果"。好的 Agent 在干活时会一路"报流水账"，这些就是痕迹。主要看三类：

| 痕迹 | 长什么样 | 你该看什么 |
|-|-|-|
| 步骤说明 | "我先读文件 A""接下来分 3 步""第 2 步我改了 XXX" | 它是否按你任务书的顺序走，有没有跳过哪一步 |
| 改动的文件 | 它说"已修改 summary.py""新增了数据表.csv" | 它到底碰了哪些文件，有没有碰你没让它碰的 |
| 运行输出 | 它跑完打印出来的结果，或报错信息 | 结果对不对、报错是哪个环节出的 |

> 记一个类比：**痕迹就是 Agent 的"行车记录仪"。** 出了事，你第一时间调行车记录仪，而不是反复问司机"你刚才干嘛了"。

## diff 是什么：AI 的"改动清单"

**结论一句话：diff 就是"改动清单"——它每改一次，给你列清楚哪些文件动了、哪些行加了、哪些行删了。你不用会写代码，也能读。**

diff 是 Agent 干活后最常用的一种痕迹。把它想成**文档的"修订记录"**：你在 Word 里开过"修订"模式吗？谁加了字、谁删了字，都用颜色标出来。diff 就是程序世界的修订记录。

读 diff 时，你**不需要看懂代码语法**，只看三件事：

1. **动了哪个文件**——清单开头会写文件名；
2. **大概加了什么、删了什么**——加的行前面有 `+`，删的行前面有 `-`；
3. **它说为什么改**——负责任的 Agent 会在清单下面用大白话解释改动理由。

> 下面是一段 diff 的"阅读样例"，来自小橙的文档学习助手。你不用懂代码，只练"找 `+`、找 `-`、找文件名"这三件事。

```diff
--- a/summary.py
+++ b/summary.py
@@ -3,3 +3,4 @@
-摘要 = 文章的前 100 个字
+摘要 = 文章的前 100 个字 + "……"
+如果 文章不足 100 字：
+    提示"文章太短，无法生成摘要"
```

照着三件事读一遍，你会得到：

| 你看到的 | 意思（人话） |
|-|-|
| `--- a/summary.py` / `+++ b/summary.py` | 改的是 summary.py 这一个文件 |
| 带 `-` 的一行 | 旧写法被删掉了 |
| 带 `+` 的三行 | 新加了三行：末尾补"……"、文章太短时给个提示 |
| 带 `@@` 的那行 | 定位用的"坐标"，不用管它 |
| Agent 附带的解释 | 它说自己为什么这么改（比如"防止空文章卡死"） |

> 读到这个程度就够了。**你看的是"它动了什么、理由成不成立"，不是"代码语法对不对"**——后者交给 Agent 自己负责，前者才是你的活。

## 确认点：它该在什么时候停下来问你

**结论一句话：负责任的 Agent 会在"发消息、花钱、删文件、对外发布"这类动作前停下来问你一句；这种"停下来"是安全阀，不是啰嗦。**

专业的说法叫"确认点"（guardrail，护栏）。你可以把它理解成**开车过收费站**：有些路口必须减速、交卡、等放行，不能一脚油门冲过去。

下面这几类动作，都应该有确认点：

| 动作 | 为什么必须先问 |
|-|-|
| 对外发消息、发邮件 | 发出去就收不回，错了会误事甚至丢人 |
| 花钱（调用付费服务、下单、续费） | 钱出去了很难退 |
| 删文件、覆盖原文件 | 数据没了可能找不回 |
| 对外发布（上线、公开） | 影响的是别人，不只是你自己 |

举一个老例子：**退款**。Agent 最多帮你算清楚"该退多少、影响是什么"，展示给你看；但"确认退款"这个动作，必须你自己点。这就是确认点——它算，你拍板。

**两个极端都是问题：**

- **"每次都问"**——问到你烦，说明它把小事也当大事，效率太低；
- **"从不问"**——该刹车时不刹车，最危险，尤其碰钱和删除。

> 一句话原则：**读、查、算可以放开干；发消息、花钱、删文件、对外发布必须停下来问你。** 判断标准就一句——"这个动作能不能反悔？"

## 什么时候让它停、什么时候可以重试

**结论一句话：网络卡了可以重试，需求没说清不该重试，碰钱的动作绝不盲目重试。**

旧版教材里有一张"重试决策表"，全是工程师术语。这里把它改成人话，你只需记住三种情况：

| 遇到的情况 | 该不该让它重试 | 怎么做 |
|-|-|-|
| 网络波动、超时、临时卡顿 | 可以，重试 1–2 次 | 让它再跑一次，并把这次的出错信息一并给它 |
| 参数没给全、需求没说清 | 不该重试 | 先停下，把缺的信息补给它再继续 |
| 涉及钱、删除、对外发送的动作 | 绝不盲目重试 | 先查"动作到底发生了没有"，再决定下一步 |

> 核心心法：**重试解决的是"临时故障"，不是"没交代清楚"。** 需求错了重试一百次还是错，还会把时间和钱都搭进去。

## 别一次放权做太多

**结论一句话：一次让它"全自动干完一整套"，出问题你连哪一步错了都不知道；正确做法是小步放权、逐步确认。**

想象你第一次让一个新人独立办事，就给他"帮我处理公司所有报销"——他大概率会翻车，而且你不知道他翻在哪一步。让 Agent 干活也一样：

| ❌ 一次放权太多 | ✅ 小步放权 |
|-|-|
| "帮我把整个应用做好并发布" | "先改'摘要'这一步，改完给我看改动清单，我确认后再改下一步" |
| 出了问题说不清卡在哪 | 每步都有确认点，卡在哪一步一眼看到 |
| 出了大错要整个推翻 | 只推倒一小步，代价小 |

> 小步放权不是不信任它，而是**让你的验收能跟上它的速度**。它越能干，你越要分步放行。

## 小橙第一次放行：先看清单，再点头

小橙到了 L3，她的文档学习助手已经能做"生成摘要"了。这一天她想让 Agent 加一个新功能："如果文章太短，就提示用户，别生成空摘要。"

Agent 动手后，没直接说"做完了"，而是先甩给她一份改动清单（就是前面那份 diff），还附了一句解释："我改了 summary.py，加了空文章的判断，这样空文章不会再卡住。"

小橙照着本章的方法读了清单：

1. **动了一个文件**（summary.py），没碰别的——符合预期；
2. **加了三行、删了一行**，方向对得上"加空文章提示"这个需求；
3. **解释说得通**——理由成立。

于是她回复"可以，继续"。三分钟后 Agent 跑出结果，她再验收功能：贴一篇 20 字的短文进去，助手果然提示"文章太短"，而不是吐一个空结果。

> 小橙做对的关键，不是她看懂了代码，而是**她检查了"动了什么、理由成不成立"再放行**。这就是本章要你练的手感。

## 常见误区

- **误区一：只看最终结果，不看过程。** Agent 说"完成"不等于真完成；痕迹和改动清单才是你判断的依据。
- **误区二：以为读 diff 要先会编程。** 读 diff 只需要找"文件名、`+`、`-`、解释"，不需要懂语法。
- **误区三：把"它问得多"当成缺点。** 关键动作前多问一句是安全阀；完全不问的才危险。
- **误区四：一出错就让它重试。** 需求没说清时，重试没用，先补信息再继续。
- **误区五：一次放权让它从头干到尾。** 大任务拆小步、每步确认，你才 hold 得住。

## 本章验收

- [ ] 能说出 Agent 干活的三种痕迹（步骤说明、改动文件、运行输出）；
- [ ] 拿到一份 diff，能指出"动了哪个文件、加了什么、删了什么"；
- [ ] 能说出一句"确认点"的原则（读查算可放开，发花删发要问）；
- [ ] 能举出一个"该重试"和一个"绝不该盲目重试"的例子；
- [ ] 完成一次"看痕迹 → 读改动清单 → 放行/喊停"的练习并记录在任务卡。

## 可选动手（想做就做，不做不影响主线）

**第一次读真实 diff：** 如果你用的是开发型 Agent（Codex / Claude Code / Cursor），给它下一个小改动任务，命令它"改完先给我看改动清单，我确认后再继续"。拿到清单后，用本章的三件事读一遍，再决定放行。

如果手边只有问答型 AI，做不了 diff 也没关系——把本章的 diff 阅读样例再读一遍，能对着说清"动了哪个文件、加了什么、删了什么"就算过关。
