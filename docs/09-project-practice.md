# 09｜完整项目实战

> P3 的目标不是堆功能，而是完整经历一次真实项目：理解问题、做出 MVP、验证效果、处理失败、部署和复盘。

## 先选一个小而真实的问题

可以从销售、科研、客服、CRM、采购、运营、材料或数据分析中选题，但必须满足：有明确用户、有真实输入、有可观察输出、有失败代价。

不要从“我要做一个行业 Agent”开始。先写成一句可验收的任务：

```text
帮助 [哪类用户] 从 [什么输入] 得到 [什么输出]，
输出必须满足 [质量标准]，在 [高风险情况] 下转人工。
```

## 项目分五个版本

### V0：手工流程

不用代码，拿 3 个真实样例手工走一遍。确认用户真的需要这个结果，而不是你喜欢这个技术。

### V1：最小可运行

只做一条主链路：输入、一次模型调用、输出和错误提示。能从干净环境复现。

### V2：可验证

加入结构化输出、测试集、日志和失败样例。此时开始比较 Prompt、模型或流程改动。

### V3：可连接

接入一个知识库或外部工具，明确权限和人工确认。不要一次连接五个系统。

### V4：可交付

完成部署说明、架构图、演示视频、成本与延迟记录、风险说明和回滚方法。

## 项目文档模板

```markdown
# 项目名称

## 用户和问题
谁在什么场景下遇到什么麻烦？

## 不做什么
明确边界，避免变成万能系统。

## 输入与输出
给出真实样例和字段定义。

## 方案取舍
为什么用普通调用 / Workflow / RAG / Agent？

## 失败处理
超时、无依据、权限不足和工具失败怎么办？

## 评估方法
测试集、指标、人工检查和版本对比。

## 部署与回滚
别人如何运行，坏了如何退回？
```

## 架构不要画得比项目大

第一版可能只需要：输入层、应用逻辑、模型接口、结果存储。只有当问题真实出现时，再加入向量库、队列、Tracing 或 Agent 编排。

架构图应该能回答：数据从哪里来、经过什么处理、什么时候调用模型、哪里可能失败、哪些步骤需要权限。

## 评估要贴近用户

为项目准备三类样例：

- 正常样例：系统应该顺利完成；
- 边界样例：输入太短、太长、缺字段或资料过期；
- 失败样例：模型超时、知识库没有答案、工具权限不足。

每个样例都写期望行为，不只写“回答正确”。例如“没有依据时拒答”本身就是正确行为。

## 用户反馈怎么收集

演示给 3–5 个目标用户，问四个具体问题：

1. 你原来怎样完成这件事？
2. 哪一步最省时间？
3. 哪个输出让你不敢信？
4. 如果只能改一件事，改什么？

把反馈转成待办，并标记是需求问题、质量问题、交互问题还是安全问题。

## 最终交付包

- 可复现的代码和配置说明；
- 一个 3–5 分钟演示；
- 架构图和关键决策记录；
- 至少三个失败案例及修复；
- 评估集和一次前后对比；
- 权限、隐私和成本说明；
- GitHub README 和面试讲解稿。

## 本章验收

- 能从需求写出明确边界；
- 有一个从 V0 到 V4 的版本记录；
- 能演示成功和失败两条路径；
- 能解释自己的技术取舍；
- 能让别人从 README 复现项目；
- 能回答“如果换模型或框架，哪些部分不变”。

## 进一步小白练习

## 一个 14 天的 P3 实施节奏

| 天数 | 任务 | 当天证据 |
| --- | --- | --- |
| 1 | 访谈或写出用户场景 | 需求卡片 |
| 2 | 收集 3 个真实样例 | 脱敏输入集 |
| 3 | 手工完成流程 | 基准答案 |
| 4–5 | 完成 V1 最小链路 | 可运行 Demo |
| 6 | 加入结构化输出和错误处理 | 失败样例 |
| 7 | 写评估集 | 10–20 个 case |
| 8–9 | 加入 RAG 或一个工具 | 调用日志 |
| 10 | 加权限、确认和边界 | 风险清单 |
| 11 | 优化一次质量或延迟 | 前后对比 |
| 12 | 部署或整理复现环境 | 部署说明 |
| 13 | 录演示并找人试用 | 用户反馈 |
| 14 | 写 README 和复盘 | 作品集初稿 |

每天只推进一个可验收结果。如果某天没有写代码，也可以完成评估集、架构图或失败复盘。

## 需求变更怎么办

把新想法放进“候选池”，不要立刻插入主线。每个候选都写用户价值、实现成本、风险和是否影响当前验收。只有能改善核心指标或解除阻塞，才进入当前迭代。

## 本节练习

为自己的 P3 写一页项目启动文档，并把所有功能分成“本周必须有、之后再做、明确不做”三栏。

## 第二轮小白练习

## 每个版本都要回答“为什么继续”

V0 结束时问：用户真的需要吗？V1 结束时问：最短链路跑通了吗？V2 结束时问：结果能检查吗？V3 结束时问：连接外部系统的收益是否大于风险？V4 结束时问：别人能复现、使用和接管吗？

如果答案是否定的，就先修当前版本，不要继续堆功能。一个只有三个功能但证据完整的项目，通常比拥有二十个按钮却无法解释的项目更适合作品集。

## 项目复盘的五句话

完成后尝试只用五句话讲清楚：我为谁解决什么问题；最小方案是什么；哪一次失败最有价值；哪项指标变好了；下一步为什么不是继续加功能。说不清楚时，回到需求卡片和评估集，而不是继续写代码。

## 本章最终产物

需求卡片、版本记录、架构图、评估集、失败复盘、演示视频、README 和面试讲解稿，共同组成 P3 交付包。

## 第三轮小白练习

## 从今天开始怎么启动项目

如果你还没有选题，先不要搜索“最酷的 AI 项目”。观察自己每天遇到的一件重复麻烦：资料难找、表格难整理、信息难比较、规则难查询。用 15 分钟写三个真实例子，再选一个最容易获得输入和反馈的。

第一天不写 Agent。先用人工方式完成一次任务，并把你做过的步骤全部写下来。人工流程就是未来系统的参考答案；如果人工自己都说不清步骤，程序和模型更不可能凭空解决。

## 项目卡片示例

```text
项目：课程资料学习助手
用户：准备考试的学生
输入：课程讲义和一个问题
输出：简短解释、原文依据、下一步练习
不做：不替学生做最终判断，不连接支付或发送系统
成功：20 个问题中至少 17 个引用正确，资料没有答案时拒答
反馈：请三位同学试用并记录他们看不懂的地方
```

这张卡片比“做一个教育 Agent”更容易实现、测试和复盘。

## 每次迭代只回答三个问题

这次改动解决哪个用户问题？用什么证据证明解决了？引入了什么新风险？如果答不出来，先不要合并改动。项目管理的核心不是把待办清空，而是让每一次改变都有理由。
