# 09｜完整项目实战

> 💡 **提示**
> 这一章不是再做一个 Demo，而是完成一项完整交付：从真实需求、方案取舍、实现、测试、部署到用户反馈迭代。

# 本章解决什么问题

前面的 P1 和 P2 让你掌握局部能力，P3 要求你把它们组合成一个真实项目，并能向用户和面试官解释为什么这样设计。

# 项目选题与边界

| 方向 | 可选项目 | 优先验证的业务指标 |
| --- | --- | --- |
| 科研 / 材料 | 文献证据助手、实验记录助手、材料知识 Agent | 检索命中、引用准确、节省阅读时间 |
| 销售 / CRM | 客户调研、线索总结、跟进建议助手 | 信息完整、建议采纳、人工节省 |
| 客服 / 运营 | 知识库客服、工单分流、运营分析助手 | 解决率、转人工率、错误升级 |
| 采购 / 企业协同 | 询价比较、供应商资料助手、审批预审 | 比价准确、审批时间、越权风险 |
| 数据分析 | 指标问答、报表解释、异常分析 Agent | 答案正确、SQL 安全、分析耗时 |

选题规则：一个明确用户、一类高频任务、一个可获得的数据源、一个可度量的改进指标。禁止用“万能助手”作为项目范围。

# 完整交付流程

1. **需求：**访谈或模拟 3 位用户，写用户故事、频率、当前流程、失败代价和不做什么。
2. **可行性：**判断哪些步骤适合模型，哪些必须由程序、数据库或人工完成。
3. **架构：**画输入、模型、Workflow、Agent、RAG、Tool、数据库、权限、日志和部署边界。
4. **原型：**先完成最小 happy path，再加入反例、权限和人工确认。
5. **工程化：**补 schema、错误、重试、停止条件、Evaluation、Tracing、成本和延迟。
6. **交付：**部署一个可复现版本，记录版本、环境、测试结果、限制和回滚方式。
7. **迭代：**收集用户反馈，选择一个问题改进，用数据证明变化。

# 架构决策模板

| 决策 | 必须说明 |
| --- | --- |
| 模型 | 任务需要的能力、速度、成本、隐私和替换方案 |
| Workflow 或 Agent | 动态性带来的收益、状态、停止条件和对照方案 |
| RAG | 知识来源、更新频率、版本、权限、检索和引用策略 |
| Tool / MCP | 工具边界、参数、权限、风险、人工确认和失败处理 |
| 数据与部署 | 存什么、保留多久、谁能看、如何监控、如何回滚 |

# AI Coding 学习方法

按小任务推进：先让 AI 写需求澄清和测试，再实现一个垂直切片。每次合并前必须阅读 diff、运行测试、检查安全和更新决策记录。要求 AI 生成替代方案，但由你选择并写下理由。

# 自己修改

- 删除一个“看起来很智能但无法验收”的功能，缩小范围。
- 为 P3 增加一个人工确认步骤，并说明它保护了什么风险。
- 替换模型或框架实现，保留相同测试集，比较结果。
- 把一次用户反馈转成可复现测试和版本变更。

# Debug 挑战

进行一次故障演练：模型超时、知识库无命中、工具返回 403、用户重复提交、日志缺失。每次都要从 run_id 找到故障步骤，给用户可理解的反馈，并证明没有重复副作用。

# 最终交付清单

- 需求文档、范围边界、用户故事和风险清单。
- 架构图、数据流、权限矩阵、Prompt / schema / 工具版本。
- 可运行 Demo、部署地址或一键复现方式、README 和环境变量示例。
- 测试集、Evaluation 报告、Tracing 样例、成本和延迟报告。
- 至少 3 个失败样例、一次用户反馈迭代、一次事故或故障复盘。

# 验收标准

- 能在 10 分钟内演示完整用户路径，并说明每次模型调用和外部动作。
- 能解释关键架构取舍、替代方案、失败处理和安全边界。
- 能让别人根据 README 在新环境复现核心链路。
- 能拿出数据说明项目解决了什么问题，而不是只展示聊天界面。
- 能回答换模型、换框架、知识更新或权限变化时需要改哪里。

# 自测与常见误区

- 我的项目是否只有功能，没有用户、指标和失败代价？
- 我是否把 AI 的贡献和自己的工程决策分开记录？
- 为什么项目越大不一定越有价值？范围过大导致无法验证、无法交付和无法复盘。
- 常见误区：堆功能；只演示 happy path；没有真实或合成测试集；没有权限；README 不能复现；没有限制说明。
