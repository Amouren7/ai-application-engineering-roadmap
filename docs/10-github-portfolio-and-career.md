# 10｜GitHub 作品集与求职

> 🎒 **提示**
> 招聘方要看的不是“用了多少 AI 名词”，而是你能否把真实问题做成可运行系统，并解释取舍、失败和验证。

# 本章解决什么问题

很多项目停留在截图和一句“基于 Agent 的智能助手”。本章把 P1、P2、P3 变成可验证的 GitHub 仓库、演示、简历 bullet 和面试回答。

# 岗位能力映射

| 岗位名称 | JD 中真正要看 | 你的证据 |
| --- | --- | --- |
| AI Application Engineer | LLM API、Workflow、RAG、评估、部署 | P1 / P2 / P3 |
| Agent Engineer | 工具、状态、循环、记忆、可靠性和安全 | 04、06、07、08 的实现与轨迹 |
| AI Automation Engineer | API、外部系统、自动化流程、权限和运维 | Workflow 和连接器项目 |
| AI Solutions Engineer / FDE | 需求理解、客户沟通、快速原型、交付和反馈 | 需求文档、演示、复盘和用户反馈 |
| Solutions Architect / AI 产品技术 | 系统边界、成本、风险、扩展和技术取舍 | 架构决策记录和对照实验 |

看 JD 时圈出动词：build、integrate、evaluate、deploy、debug、own、talk to users。岗位名称可以变化，能力动词更稳定。

# GitHub README 模板

1. 一句话：为谁解决什么问题。
2. Demo：截图、短视频或可访问演示，以及已知限制。
3. 架构：数据流、模型调用、RAG、Tool、Agent、数据库和部署。
4. 快速开始：环境、依赖、配置、运行、测试和清理。
5. 评估：测试集、指标、baseline、结果和失败样例。
6. 工程：日志、Tracing、权限、隐私、成本、延迟和回滚。
7. 决策：为什么选 Workflow / Agent、模型和框架，替代方案是什么。
8. 贡献：AI Coding Agent 帮了什么，你做了哪些 Review 和修改。

# 简历表达公式

用“问题 + 动作 + 工程手段 + 结果 + 证据”写 bullet，不写“学习了 LangChain”。例如：为内部政策问答构建带版本过滤和引用校验的 RAG 服务，使用 30 条测试集比较关键词与混合检索，降低无依据回答并记录 P95 延迟。

# 面试题库

| 问题 | 回答必须包含 |
| --- | --- |
| 为什么用 Agent？ | 动态性、对照 Workflow、收益、成本和停止条件 |
| RAG 效果如何验证？ | 测试集、Recall@k、引用支持率、回答正确率和人工抽检 |
| 遇到过什么故障？ | 现象、定位路径、根因、修复、回归测试和预防 |
| AI 帮了你什么？ | 生成、解释、反例和重构；你做的判断、Review 和验证 |
| 如何控制成本和风险？ | 输入、模型、缓存、预算、权限、人工确认和监控 |

# 跟着做

1. 选一个项目，删除无关文件和未使用依赖，确认 README 可以从零运行。
2. 写一份架构图和 3 分钟演示脚本，演示一个成功和一个失败场景。
3. 把一次技术决策写成 ADR：背景、选项、选择、代价、后悔条件。
4. 用简历语言写出三条成果，每条都附测试、指标或演示证据。
5. 根据 3 个目标 JD 建立“要求 → 证据 → 缺口 → 下一步”表格。

# 验收标准

- 陌生人能通过 README 运行项目并理解限制。
- 你能不看稿讲清数据流、模型调用、工具、权限、评估和故障。
- 能把岗位 JD 转成能力清单，而不是只看“AI 工程师”五个字。
- 能诚实说明 AI 辅助范围和自己承担的工程决策。

# 常见误区与下一步

- 误区：README 只有安装命令；只放截图；夸大指标；隐藏失败；堆砌框架名；不说明数据来源。
