# 10｜GitHub 作品集与求职

> GitHub 不是代码仓库的陈列柜，而是别人判断你能否独立交付的证据包。

## 一个好的 README 先回答什么

读者通常只花几十秒决定是否继续看。README 开头应该直接说明：这是给谁用的、解决什么问题、结果长什么样、如何运行。

推荐顺序：

1. 一句话项目说明；
2. 截图或演示链接；
3. 真实问题和使用流程；
4. 快速运行；
5. 架构和数据流；
6. 评估与失败案例；
7. 安全、成本和限制；
8. 后续计划。

不要先放十个徽章、长篇技术名词和没有上下文的代码片段。

## 推荐的仓库结构

```text
project/
├─ README.md
├─ src/                 # 应用代码
├─ tests/               # 固定评估和单元测试
├─ examples/            # 可公开的输入输出样例
├─ docs/                # 架构、决策、故障复盘
├─ .env.example         # 变量名，不放真实值
├─ requirements.txt
└─ LICENSE
```

目录不必完全一样，但读者要能快速找到入口、测试和说明。

## 作品集要展示“你决定了什么”

只说“使用了 LangGraph、RAG、MCP”不能证明能力。更有价值的是：

- 为什么这个任务不用 Agent；
- 为什么选混合检索；
- 模型没有依据时如何拒答；
- 写入动作如何确认；
- 你发现过哪个故障；
- 修改后哪个指标变好了，代价是什么。

技术名词是工具清单，决策记录才是工程证据。

## 如何写一次失败案例

```text
现象：回答引用了错误章节
复现：问题“实习生交通费上限是多少”
原因：关键词检索命中旧制度，metadata 没有生效日期
修复：加入生效日期过滤，并在结果中展示来源日期
验证：20 条评估问题中引用正确率从 70% 提升到 90%
剩余限制：跨制度比较仍需人工确认
```

这比“优化了 RAG 效果”更容易让面试官理解你的能力。

## Git 提交也能展示思路

把大改动拆成有意义的提交：

```text
feat: add document input
feat: validate structured output
test: add citation evaluation set
fix: handle empty retrieval result
docs: explain deployment and limits
```

提交前检查 diff，确认没有密钥、个人隐私、临时文件或调试输出。

## 面试讲解的五分钟结构

1. 场景：谁遇到什么问题；
2. 方案：输入、处理、输出和架构；
3. 关键决策：为什么选这个方案；
4. 故障：最难的问题如何定位和修复；
5. 证据：指标、用户反馈、成本和下一步。

如果对方追问“模型换了怎么办”，回答系统哪些能力依赖原理、哪些依赖具体 SDK，以及你会如何重新评估。

## 本章行动清单

- 为 P1、P2、P3 各写一句项目说明；
- 给每个项目补一个成功样例和三个失败样例；
- 把一个 README 交给没有背景的朋友试读；
- 删除所有不必要的敏感信息；
- 录一段不超过五分钟的演示；
- 写一页“我做了什么决定”。

## 本章验收

- 别人能在 5 分钟内运行或理解项目；
- README 有真实样例、限制和评估证据；
- 能解释至少一次失败的根因；
- 能说清 AI 做了什么、你决定了什么；
- 作品集没有把“调用 API”包装成“训练了模型”。

## 进一步小白练习

## 可直接套用的 README 骨架

```markdown
# 项目名称

一句话：给谁解决什么问题。

## Demo
截图、短视频或在线地址。

## 快速运行
安装、环境变量、命令和示例输入。

## 工作原理
用一张图说明输入、模型、检索、工具和输出。

## 评估结果
测试集、指标、版本和限制。

## 失败案例
至少写三个真实问题和修复过程。

## 安全与限制
权限、隐私、成本、不能做什么。
```

如果 README 只有“技术栈：Python、RAG、Agent”，读者仍不知道项目有什么用。技术栈应该服务于问题说明，而不是替代问题说明。

## 面试追问模拟

请自己回答：为什么不用普通搜索？为什么不用 Agent？检索错了怎么办？模型换了怎么办？成本怎么测？如果工具返回未知状态怎么办？

每个答案都尽量包含一个事实证据或实验结果。不能回答的问题，就是下一轮项目迭代的学习清单。

## 本节练习

把你的 README 发给一个不了解项目的人，只让他看 3 分钟，然后请他复述“项目解决什么问题、如何运行、有什么限制”。复述错误的地方就是 README 需要改的地方。

## 第二轮小白练习

## 把项目翻译成别人听得懂的话

技术表达：“我做了 RAG Agent。”

更好的表达：“我做了一个给新员工查询制度的助手。它先按生效日期检索制度片段，再生成带引用的回答；资料没有依据时拒答，提交申请前必须人工确认。20 条测试问题中，引用正确率从 70% 提升到 90%。”

后一个说法同时交代了用户、链路、边界和证据。简历、主页和面试都应该优先使用这种表达。

## 发布前自查

在公开仓库前搜索密钥格式、个人信息、内部域名、临时文件和不可公开的样例。确认安装命令在干净目录可运行，确认截图与当前版本一致，确认 README 中的限制没有藏起来。

## 本章最终产物

一个 30 秒能看懂的项目简介、一个 3–5 分钟演示、一个可复现 README、一次失败复盘和五个面试追问答案。
